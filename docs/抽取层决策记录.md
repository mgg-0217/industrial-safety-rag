# 抽取层决策记录 —— 要不要修抽取层并重跑

> PRD 第 9 节 M3 的验收标准之一：「**产出"是否重跑抽取层"的决策记录**
> （3.1 策略 4 的 (a)/(b) 两条路，选了哪条、为什么）」。
> 决策日期 **2026-11-02**，决策人：项目负责人。

---

## 1. 决策点是什么

PRD 3.1 策略 4 的第 4 条把这件事明确标成 **M3 的前置决策点**：

> **是否修抽取层**：修 `pdf_to_md.py` 让它不无条件注入表头是根治办法，
> 但要**重跑抽取**，会改变全部 26 份 md，进而改变所有下游数字
> （字符数、表格块数、评测候选）。**这是 M3 的前置决策点**，不是 M3 内部能顺手改的。
> 两条路都可行：(a) 修抽取层并重跑（数据更干净，但所有基线数字要重算）；
> (b) 不重跑，在切分层做表头校验（成本低，但伪表仍留在语料里）。
> **倾向 (b)**：本项目的价值在切分/检索/版本治理，伪表只影响表格切分策略的效果，
> 而重跑会作废已核实的全部事实基线。

**PRD 当时倾向 (b)**，理由是：已知的抽取层缺陷只有"表头是假的"这一条，
它只影响策略 4 的效果，不影响别的。

**2026-11-02 发现了一个大得多的问题**，PRD 的这个前提不再成立 —— 见第 2 节。

## 2. 触发本次决策的新发现

### 2.1 现象

`data/md/AQ_T3034_2022_huagong_anquan.md`（化工过程安全管理导则，59 页、41 张表，
本项目**最大的一份文档**）的正文**读不通**：

```
４１２ 企业主要负责人应领导企业贯彻落实 以人为本 安全第一 的安全理念 建立包括以安全愿景
．． “ 、 ” ,
目标 安全发展战略 安全使命精神等为内容的安全生产核心价值观 构建符合企业安全生产特点的良
、 、 ,
好安全文化
```

条款号 `4.1.2` 被撕成 `４１２`（第一行）+ `．．`（第二行）；
中文标点与 ASCII 片段被甩到下一行。

### 2.2 根因：**不是 PDF 的错，是抽取层的错**

`tools/pdf_to_md.py` 用 `page.extract_text()` 取文本。pdfplumber 计算字符 bbox 时
**用的是字体度量（ascent/descent）**，而该 PDF 的中文与 ASCII 用**两套字体**，
两套字体的度量不一致 —— bbox 的 `top` 整体错位 **8.5pt**。
pdfplumber 默认 `y_tolerance=3`，只把 `top` 相差 ≤3pt 的字符算同一行，
于是同一视觉行被拆成 3–4 条"行"。

**PDF 本身完全正常**：用 pypdfium2 渲染 300dpi 后逐行核对，版式、条款号、
拉丁文本的位置全都对（`data/_diag/aq_p10_line.png`）。

**真实基线在文本矩阵里**（`char['matrix'][5]`），不在 `top` 里：

| 行 | pdfplumber 的 `top` | **真实基线** | 字体 |
|---|---|---|---|
| 中文正文 | 132.30 | **702.65** | FZSSK--GBK1-0 |
| 条款号数字 | 133.90 | **701.39** | E-FZ |
| 标点 | 139.30 | **702.94** | E-BZ |
| 条款号句点 + `GB/T37243` | 140.90 | **701.39** | E-BZ |

按 `top` 分行 → 4 行；按基线分行 → **1 行**（基线跨度 1.55pt，真实行距 15.91pt）。

### 2.3 影响有多大：这份文档**一条候选题都出不来**

`build_eval_candidates.py` 的条款正则要求**半角** `\d+[\.、]`，
而 PDF 字体把 `4.1.2` 映射成**全角** `４．１．２`（渲染出来是正常的半角，
是 ToUnicode CMap 的映射问题）→ 切不出条款。

实测：

| | AQ_T3034 切出的条款数 |
|---|---|
| 修复前 | **0** |
| 基线重建后（未归一化） | 8 |
| 基线重建 + 全角归一化后 | **300** |

**项目里最大、最权威的一份文档（行业标准 AQ/T 3034—2022）在评测池里完全缺席**，
它的 `clause_no` 引用也是坏的。

### 2.4 修法与验证

**修法**（`src/pdf_lines.py`）：按**文本矩阵基线**归并成行 → 行内按 `x0` 排序。

关键点是错位出去的 run **x 坐标仍在原位**（实测 `．．．` 在 x=76.5、
`GBT３７２４３` 在 x=408，正好在"按照"与"的要求"之间），
所以按 x 重排就还原了阅读顺序。

**验证方法：用 OCR 当独立裁判**（`tools/validate_rebuild_vs_ocr.py`）。
把页渲染成位图 → rapidocr 识别 → 与抽取文本比字符相似度。
OCR 只看像素，**不经过 pdfplumber 的任何逻辑**，是独立于抽取层的外部真值。

| 文档 | 页 | 修复前相似度 | 修复后 | 变化 |
|---|---|---|---|---|
| AQ_T3034 | 4 | 0.8162 | **0.9112** | +0.0950 |
| AQ_T3034 | 6 | 0.8104 | **0.8895** | +0.0791 |
| AQ_T3034 | 10 | 0.7305 | **0.8534** | +0.1229 |
| AQ_T3034 | 20 | 0.7507 | **0.8573** | +0.1066 |
| AQ_T3034 | 33 | 0.6148 | **0.7432** | +0.1284 |
| mem_xianshi_shouce | 20 | 0.8822 | 0.8822 | 0（本来就干净） |
| mem_xianshi_shouce | 38 | 0.9389 | **0.9546** | +0.0158 |
| mem_2019_78 | 5 / 30 | 0.9762 / 0.9498 | 同 | 0（本来就干净） |
| **平均** | | **0.8300** | **0.8908** | **+0.0608** |

**每一页都持平或更好，没有任何一页回退。**

**容差是扫参出来的，不是拍的**（`tools/sweep_baseline_tol.py`）：
基线容差 2.0–4.0 的得分**完全相同**（0.8908），≥5.0 开始掉（0.8785，
相邻两行被并成一行），≤1.5 开始掉（0.8891，行被拆开）。
取平台中部 **3.0**（也正好是 pdfplumber 自己的默认 `y_tolerance`）。

## 3. 决策：**走 (a) 修抽取层并重跑**

PRD 原倾向 (b)，但 2026-11-02 的新发现推翻了它的前提：

| | PRD 当时的假设 | 实际情况 |
|---|---|---|
| 抽取层缺陷 | 只有"表头是假的" | 还有"正文行序错乱"，影响**全部 5 份 PDF 的正文** |
| 影响面 | 只影响策略 4 的效果 | **最大文档 0 条候选**，正文不可读、引用不可展示 |
| 基线作废成本 | "所有基线数字要重算" | 候选池 842 → 1124；**题集 306 条的题干与数值锚点全不变**，只有 4 条的 `clause_no` 因下标归位而变（已自动重挂） |

**更重要的是时机**：M2 的 306 条题**全部还是 `review_status=pending`**，
用户还没逐条核对过。现在重跑 → 题集不用返工；
等核对完再重跑 → 人工核对成本翻倍。

### 3.1 实际影响面（已核对）

| 项 | 变化 |
|---|---|
| 语料 md | **5 / 26 份变化**（5 份 PDF），21 份 HTML 未动 |

## 4. 顺带修掉的两个真 bug

重跑过程中发现另外两个**独立于抽取层**的 bug，一并修了。

### 4.1 策略 4 的表头整个丢了 🔴

`parse_table()` 返回 `(数据行, 表头)`，但 `_scan_blocks()` 只把**数据行**存进
`b.rows`，表头只用来做了个布尔判断就被丢弃；而策略 4 又用 `rows[0]` 当表头 ——
于是**第一条数据行被当成表头重复了一遍，真表头彻底消失**。

实测（`mem_xianshi_shouce` 的有限空间分类表）：

| | 值 |
|---|---|
| 表格真实表头 | `有限空间 种类 \| 有限空间 \| 作业可能存在的主要安全风险` |
| chunk 里存的"表头" | `地下 有限空间 \| 废井、地坑、地窖、通信井 \| 缺氧、高处坠落`（**第一条数据行**） |

PRD 3.1 策略 4 明写「表头行原样存进 chunk 的 `text` 开头（不是只存 metadata）…
行级答案（"导线型号"）必须带表头才成立」—— 这条根本没做到。

修法：`Block` 增加 `header` 字段，表头与数据行**分开存**。

### 4.2 键值对表判据误伤最表格密集的文档 🔴

旧判据是"非空格占比低 + 各行非空格数差异大"。
但 PDF 表格的**单元格内容会跨行折行**，pdfplumber 把一个逻辑行拆成多条物理行
（每行只剩 1–2 个非空格）→ `mem_2019_78` 的 **17 张排查表**
（`序号|排查内容|排查依据`，每张 50–76 行）全被判成键值对 →
策略 4 对**表格最密集的文档**一张表都不切，PRD 的表格切分能力作废。

真区别在**横向分布**：折行表的内容集中在**相邻**列（1 段），
键值对表的内容**散在**不相邻的列（≥2 段）。改判据后：

| 文档 | 修复前（真表头/伪表/键值对） | 修复后 |
|---|---|---|
| `mem_2019_78` | 14 / 4 / **17** | **35 / 0 / 0** ✓ |
| `AQ_T3034` | 20 / 10 / 11 | 36 / 2 / 3 |
| `mem_xianshi_shouce` | 13 / 28 / 0 | 13 / 28 / 0（不变） |
| `kaiping_zuoyepiao` | 0 / 0 / 2 | 0 / 1 / 1 |
| `gaoqing_yuxian_kongjian` | 0 / 0 / 2 | **2 / 0 / 0** ⚠️ 见下 |

## 5. 与 PRD 的人工判定不一致的地方（如实记录）

PRD 3.1 策略 4 有一张"首行像表头"的逐文档实测表（122 块 / 78 块像表头）。
新的启发式给出 **86 块**，逐文档差异：

| 文档 | PRD 人工判定 | 新启发式 | 差异原因 |
|---|---|---|---|
| `AQ_T3034` | 31 | 36 | 键值对特判收窄后，更多表进入表头判定 |
| `mem_xianshi_shouce` | 11 | 13 | 同上（PRD 的 30 块散文首行仍然是 28 块） |
| `gaoqing` | **0** | **2** | ⚠️ 见下 |
| `kaiping` | 0 | 0 | 键值对特判仍生效 |
| `mem_2019_78` | 35 | **35** ✓ | 一致 |

**`gaoqing` 的差异**：PRD 判"两块都是键值对形式，无表头概念"。
实际打开看，两块表都有**清晰的表头**：

```
| 序号 | 被检查单位（企业） | 问题描述 | 整改措施 | 是否已完成整改 | 责任单位 |
| 单位名称 | 派出检查组（个） | 检查企业数量（家） | 发现问题数量（项） | ... |
```

判为"无表头"会让它整表一块、不切行；而它的数据行几乎全是 `...` 占位符，
信息量极低 —— 切不切差别都不大。**以实测为准：它有表头，按有表头处理。**

> ⚠️ 这个差异说明 PRD 的人工判定表**需要按新启发式重新校准**。
> 本记录先如实留痕，PRD 的表格更新排在 M4 之前做（不影响 M3 验收）。

## 6. 这次决策没有解决的事（诚实清单）

- **`«»` 编码问题**：PDF 字体把 `《》` 映射成 `«»`（AQ_T3034 里 7 处）。
  归一化层没管这个，量很小，暂不动。
- **表格的逻辑行还原**：折行单元格导致的"物理行 ≠ 逻辑行"问题，
  本次只在**判据**上做了规避（不再误判成键值对），
  **没有把物理行合并回逻辑行** —— 切出来的表格 chunk 里仍有断行。
  这是策略 4 的已知上限，M4 的对比实验里应能看出来。
- **PRD 逐文档表头判定表未更新**（见第 5 节）。
- **AQ_T3034 的 300 条新条款尚未纳入正式题集** —— 按 2026-11-02 的决定，
  本轮只跑通流水线，题集维持 306 条，扩充另议。
