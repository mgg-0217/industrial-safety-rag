# 题集自动核对（M2 收尾 · 2026-11-05）

> README「下一步」第 1 项一直是"人工核对题集（**唯一挡住"结论可信"的一步**）"。
> 但 306 条逐条人读的成本很高 → 本轮的做法是：
> **机器先把能机械判的判完，只把机器判不了 / 判出问题的挑出来给人看。**
>
> 一句话结论：**306 条里机器能自动判定的占 94.8%**，
> 而且自动核对**挖出了 4 个此前没人发现的真缺陷** —— 其中一个直接让
> "事实题严格口径 0.168"这个已发布数字**失去可信度**。

---

## 1. 工具链

| 工具 | 作用 |
|---|---|
| `tools/review_eval_set.py` | **自动核对**：溯源 / 元数据 / 题型专项三层判据，输出 `data/eval/review_queue.md`（人工队列）与 `review_report.json` |
| `tools/fix_review_findings.py` | **自动修复**：把挂错的溯源条款改到锚点实际所在处；把截断的 key_point 扩展成原文整行 |
| `tools/revert_review_fixes.py` | 撤销上一批修正（key_point 变更后那批修正不再成立） |
| `tools/refine_key_points_llm.py` | **LLM 重提炼 key_point**：用项目自己的 BM25 检索 top-5 证据 → LLM 输出逐字片段 → 机器校验字面可达 |

三层判据：

* **溯源** —— 锚点必须出现在**该题指向的那个条款**里（用 `data/chunks/clause.jsonl` 的条款级原文核对）。
  这是比 `check_test_set.py` 更严的一层：后者只在 `gold_answer` 里查，
  而 `gold_answer` 本身就可能是错的。
* **元数据自洽** —— `doc_id` 在 manifest 里、数值题有保真锚点、事实题有 key_point、
  题干的量词与锚点单位对得上。
* **题型专项** —— 版本陷阱题的正答文档在该时点**确实生效**（三态判定，UNKNOWN 交人工）；
  拒答题的主体在语料里**真的不存在**（双口径精确验证：原文侧 + 归一化侧，压缩分隔符）。

## 3. 挖出的 4 个真缺陷

### 3.1 🔴 证据标记泄漏进 key_point —— 跨文档题 15/25 条中招

`doc_evidence()` 给 LLM 的证据文本每份文档前面加一行 `【<doc_id>】`
（告诉模型"这段来自哪份文档"，设计是对的）。
但**模型模仿了这个格式**，把 `【yulin_donghuo_xianshi】` 写进了 key_point；
对齐算法再忠实地把它对到证据的标记行上 →

```
key_point = 「【yulin_do」   ← 停在 8 个字符
```

这样的 key_point 在原文里**根本不存在** → `key_point_coverage` 的分母是垃圾。

**修法**：`src/eval_align.py::align_key_point` 在对齐前把标记从**两边**都剥掉
（kp 的**开头** —— 模型模仿来的标记常常没有闭合的 `】`；text 里**独占一行**的标记）。

### 3.2 🔴 事实题的 key_point 本身是"按 `clause_no` 机械切片"的产物

```
「七,事故调查7.1事故调查市市场监督管」   ← 停在"管"字，且跨了两个条款
「九,应急保障1.」
「3.2事故预防措施3.」
```

根因与 K-08 同款：**切点落在词中间**。这类片段在原文里**字面不可达**，
`check_key_point_reachable` 之所以没报，是因为它在 `gold_answer` 里查，
而 `gold_answer` 就是同一段切片产物 → **自证自洽**。

→ 🔴 **已发布的"事实题严格口径 0.168"因此不可信**：分母里混着字面不可达的碎片。

**修法**：`tools/refine_key_points_llm.py` ——
用**项目自己的 BM25** 按题干检索 top-5 证据 → LLM 输出 1–3 个**逐字片段** →
**机器校验**每个 kp 字面出现在证据里，否则丢弃。

### 3.3 溯源条款错位（预案型 / 表格型文档）

```
clause_no = "五、应急救援的初期处理措施"   ← 这个 chunk 只有 14 个字（只有标题）
kp        = "(二)压力容器安全事故应急救"      ← 实际在"六、…分项应急救援措施"下面
```

**答案没错，溯源错了**。而 `clause_no` 决定评测的 **gold 区间**
（R@5 的命中判定、`content_coverage` 的分母）→ 溯源不准 → **召回数字不可信**。

**修法**：`fix_review_findings.py` 把 `clause_no` 改到锚点**实际所在**的条款
（多命中时取**离原条款最近**的）；**数值题不改**（见 3.4）。

### 3.4 🔴 数值题的「题干问的量 ↔ 锚点」可能不匹配

```
题干：危险化学品储存场所对专用仓库和人员管理有何要求？
锚点：150 mm   ← 实际是"围堰"的数值
```

改溯源解决不了 —— **题干本身写错了**。这类题只能靠"题干 ↔ 锚点"的语义核对，
而 `check_test_set.py` 只能查**量纲**（"题干问压力、锚点却是 kg"），
查不出**主题**错位（"问仓库、答围堰"）。

## 5. 沉淀到流程里的三条

1. 🔴 **核对判据必须分题型**：拒答题的 key_point 是**判分标准**（"有没有声明查不到"），
   本来就不指向原文 —— 要求它字面可达是逻辑错误（K-13）。
2. 🔴 **"自证自洽"是最危险的假阳性来源**：在 `gold_answer` 里查 key_point，
   而 `gold_answer` 与 key_point 来自同一次切片 → 两边一起错，检查永远通过。
   → **溯源核对必须回到原文，且要到条款级**。
3. 🔴 **机器能判的和只能人判的要分开**：本轮把 306 条压到 16 条，
   剩下 16 条的共同点是"**语义对应关系**"（题干问的 ↔ 锚点答的）——
   这类问题**永远需要人或 LLM**，脚本判不了，也不该假装能判。
