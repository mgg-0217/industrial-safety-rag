# PRD 生成提示词 · 工业设备维修与安全规程问答 RAG

> **用法**：把本文件**整体**作为 prompt 交给 LLM（Claude / GPT 等），让它产出一份可直接指导实现的 PRD，存到 `docs/PRD.md`。
>
> 本文件是**自包含**的：所有事实基线已写死在里面，LLM 不需要读仓库即可开写；凡是需要它自己编的地方，本文件已明确标注"不要编"。

## 你的角色

你是一位资深 AI 系统架构师，同时熟悉工业安全管理与 RAG 工程。
你的产出物是一份**规格文档（PRD）**，读者是接下来要亲手把它实现出来的工程师（就是提出这个需求的人本人）。
因此 PRD 必须**可执行到字段级**：给出数据结构、算法选择、判定条件、验收标准，而不是"应该支持版本管理"这种无法落地的描述。

**你不认识这个项目，也不要假设任何本文件之外的上下文。**

## 一、项目一句话与背景

**项目名**：工业设备维修与安全规程问答 RAG

**一句话**：面向化工厂设备维修与安全管理人员，用一个能回答"规程怎么规定的"和"这台设备出过什么问题"的知识库问答系统，答案必须可溯源到具体条款与页码。

**要解决的问题（真实痛点，不是编的）**：
1. 安全规程、应急预案、设备完好性管理导则散落在几十个文件和几十个网页里，检修工在检修现场用手机查一条"受限空间作业氧含量限值是多少"要翻十几个链接。
2. 同一份制度存在**多个版本**，新版生效时明示废止旧版。查 2023 年的规程却拿到 2025 版、或反过来把已废止条款当现行条款执行，是真实会造成事故的错。
3. 事故调查报告里有设备位号、设计压力、故障时序这些最值钱的信息，但它们是**非结构化长文档**，人读得慢，检索系统基本召不回来。

**目标用户（两类，需求不同）**：
- **检修/工艺工程师**：查规程条款与设备参数，要条款级引用，要能翻回原文页码核对。
- **安全管理人员**：跨文档比对、做隐患排查依据，要版本状态可见（旧版是否已废止）。

## 二、元数据 schema（PRD 第二节必须照搬这一节）

> 语料主表 `data/manifest.json` 已按这套 schema 建成真实实例（27 份文档，字段 18/18 全覆盖）。**PRD 的第二节直接引用这套 schema，不要另发明一套字段名。**

字段分两层——**文档级**决定版本与溯源，**条款级**决定检索过滤与答案组装：

### 2.1 文档级（每份文档一份）

| 字段 | 类型 | 说明 | 真实取值样例 |
|---|---|---|---|
| `doc_id` | str | 文档唯一标识，同时是 `data/md/<doc_id>.md` 的文件名 | `yulin_donghuo_xianshi` |
| `title` | str | 文档标题 | `榆林市危险化学品企业动火和受限空间作业安全管理制度` |
| `doc_type` | str | 文档类型，取值来自下面 2.3 的枚举 | `安全管理制度` |
| `discipline` | str | 专业领域，可多值用 `/` 连接 | `安全/设备` |
| `doc_no` | str | 发文文号，无则填 `-` | `榆政办发〔2025〕1号` |
| `version` | str | 版本标识 | `2025版` |
| `effective_date` | str | 生效日期 `YYYY-MM-DD`，未知填 `-` | `2025-01-09` |
| `status` | str | 版本状态，**由生效区间推导**，取值见 2.3 | `有效` / `已废止` |
| `classification` | str | 公开性 | `公开` |
| `publisher` | str | 发布单位 | `榆林市人民政府办公室` |
| `source_url` | str | 原始来源 URL，用于溯源与合规复核 | `https://yl.gov.cn/...` |
| `source_format` | str | 原始件格式 | `html_webpage` / `pdf_document` |
| `raw_file` | str | 原始件文件名 | `yulin_donghuo_xianshi.html` |
| `text_file` | str | 抽取后的 md 文件名 | `yulin_donghuo_xianshi.md` |
| `chars` | int | 正文字符数 | `1826` |
| `note` | str | 人工标注备注（可选） | `第十九条明示原〔2023〕26号废止，可作版本治理正样本` |
| `extract_quality` | str | 抽取质量，取值见 2.3 | `ok` / `partial` / `failed` / `needs_ocr` |

### 2.2 条款级（chunk 级标注，随 chunk 存储）

| 字段 | 类型 | 说明 | 真实取值样例 |
|---|---|---|---|
| `hazard_tags` | list\<str\> | 危险源标签，全库共 **34 种** | `["动火作业", "受限空间作业"]` |
| `equipment_tags` | list\<str\> | 设备位号，真实位号不编造 | `["19-V-4215", "T-4200", "MP-41009-200-S1B-H1"]` |
| `maintenance_type` | list\<str\> | 维修类型 | `["故障维修", "检维修"]` |
| `ref_standard` | list\<str\> | 引用的上位标准/法规 | `["GB 30871-2022", "中华人民共和国安全生产法"]` |
| `clause_no` | str | 条款号/章节标题 | `一、事故基本情况` |
| `page_no` | int\|null | 页码锚点，HTML 源为 `null` | `12` |

### 2.3 枚举取值（PRD 里必须列全，代码里要与之对齐）

- `doc_type`（15 类）：应急预案、操作指南、安全管理制度、事故调查报告、操作手册、整改评估报告、操作规程/应急处置、应急处置指南、操作指引、操作规范、排查治理导则、行业标准、检查通知、作业票表单、检查表(表单)
- `status`：`有效` / `已废止` / `待生效`
- `extract_quality`：`ok`（完整）/ `partial`（部分，正文不全）/ `failed`（失败）/ `needs_ocr`（扫描件，需 OCR 链路）
- `source_format`：`html_webpage` / `pdf_document`

### 2.4 schema 设计上必须守住的两个判断

这两条是本项目最有技术含量、也最容易被做错的地方，PRD 要写明：

1. **`status` 是生效区间的缓存，不是独立真相。**
   判"这份文档现在是否现行"的**唯一判据是 `effective_date` 落在查询区间内**，不是去读 `status` 字段。
   `status` 只作为人工标注的辅助与展示值。这样做的好处是：同一条 `effective_from/effective_to` 区间逻辑既能判"现在"（用今天的日期），也能判"2023 年那会儿"（用查询时刻）——两套口径共用一套判据，不会出现两个地方各自算一遍算出不同结果。
   → PRD 要求：数据模型里 `status` 字段可以保留，但**判定逻辑必须走区间，不得直接信 `status`**。

2. **版本过滤发生在检索阶段，不在生成阶段。**
   已废止版本的 chunk 根本不应该进入模型上下文。让模型"自己别用过期条款"是不可靠的——prompt 约束的服从率只有 60–70%。
   → PRD 要求：过滤在检索层完成（向量库 payload 过滤 + BM25 在**过滤后的子集**上重算），过滤掉的 chunk 模型看不见。
   → 推论（也要写进 PRD）：**核心机制"先过滤再排序"与用向量还是 BM25 无关**。这条是本项目的地基——即使向量模型一个都拉不下来、只能做纯 BM25，"版本治理"这个核心机制依然成立，只损失检索召回一点质量。

## 三、事实基线（已完成的真实资产，PRD 直接引用，不要改写、不要重新编数据）

### 3.1 语料实况

- **27 份真实文档**，**34.0 万字符**，全部来自**中国政府网站公开文件**（应急管理部 / 省市应急厅 / 市政府 / 市市场监管局）。
- 文档类型覆盖 15 类；危险源标签 **34 种**；含真实设备位号（`19-V-4215`、`T-4200`、`1910-PV-42151`、`MP-41009-200-S1B-H1` 等）。
- 格式形态覆盖：**HTML 正文 / 文本型 PDF / 纯扫描件 PDF（1 份，0 字符 2 页）/ 表格密集型（导则 41 张表）/ 作业票表单**。
- **版本治理黄金样本**：榆林市动火和受限空间作业安全管理制度**两版都在库里**，2025 版第十九条明示"原《…》（榆政办发〔2023〕26号）同时废止"。这天然构成正负样本对：
  - 问 2023 年 → 应召回 2023 版
  - 默认检索 → 应过滤掉 2023 版
  - **召回到过期版本 = 直接判错**
- 抽取质量分布如实记录：完整 21 / 部分 5 / 失败 1 / 需 OCR 1（`yuncheng_paichabiao.pdf` 实测无文本层，0 字符 2 页）。
- **合规约束**：仅供内部研发与评测，不对外再分发；厂商手册因防盗链与版权不可得，**全库不含任何受版权保护的厂商文档**。

### 3.2 评测候选池实况

- **842 条候选**（`data/eval/candidates.jsonl`）：803 条事实题 + 39 条数值题（带 `must_include_numbers` 保真锚点），覆盖 15 份文档，362 条带页码锚点。
- 每条候选带：`qid / doc_id / doc_title / clause_no / page_no / question_type / question / gold_answer / must_include_numbers / hazard_tags / equipment_tags / source_url / doc_no / version / status`。
- **这是候选池，不是正式题集。** 必须经人工/LLM 精修（去重、去掉答案泄漏的表述、补齐拒答题与澄清题）后才可用于报指标。PRD 要把"精修评测集"单列为一个里程碑，并给出质检标准。

### 3.3 可复用资产（不要重复造）

- 项目一（报销预审 Agent）已完成 **扫描件 OCR 分支**：`rapidocr-onnxruntime==1.4.4`（PP-OCRv4 主引擎，带置信度）+ Windows 内置 OCR 兜底（PowerShell 调 WinRT）。项目二的 `yuncheng_paichabiao.pdf` 可直接复用这条链路验证。
- 语料抽取流水线已就位（HTML→MD、PDF→MD、PDF 类型探针、manifest 构建、评测候选生成），PRD 只需在**上游**接住，不要重写抽取。

### 3.4 本机环境约束（PRD 的技术选型必须尊重）

| 约束 | 事实 | PRD 要求 |
|---|---|---|
| `huggingface.co` | **8 秒超时、无本地缓存**（已实测） | 嵌入模型必须设计**四级降级**：镜像直连 → 小模型 → ModelScope → 纯 BM25。核心机制不依赖向量（见 2.4），降级不伤项目成立 |
| `torch` | 2.6.0 已装 | 向量路线可行，但要有降级路径 |
| PyPI | `pypi.org` 极慢（27 秒），腾讯镜像 0.5 秒 | 依赖安装一律走 `-i https://mirrors.cloud.tencent.com/pypi/simple/` |
| 嵌入服务 | 阿里云等商业嵌入 API 可用（需 key） | PRD 应同时给出"本地模型"与"API 嵌入"两条路线，并说明成本与可复现性差异 |

## 四、PRD 必含章节（10 节，缺一节即不合格）

### 第 1 节 · 背景与目标
场景、用户、两类用户各自的核心任务、**本项目明确不解决的相邻问题**（如实时监控数据接入、生产工单系统对接）。

### 第 2 节 · 语料与元数据模型
照搬第二节 schema，并补充：chunk 级需要携带哪些文档级字段（答案要能带出版本状态与来源 URL）、版本关系如何表达（`superseded_by` / `effective_from` / `effective_to` 三元组）、以及 `extract_quality != ok` 的 chunk 如何标记（**partial/failed/needs_ocr 的内容进检索会污染答案，PRD 必须给出降权或排除策略**）。

### 第 3 节 · 切分策略与对比实验设计
至少给出 6 种切分策略并**设计成可对比的实验**（同一份评测集、同一套检索、只换切分，看指标差异）：

1. **固定长度**（定长块 + 重叠）—— 朴素基线
2. **结构感知**（按标题层级切分，事故报告/导则/制度的骨架不同）
3. **条款级**（按 `clause_no` 切，保留"第X条"完整语义单元）
4. **表格切分**（按表切，行级答案需带表头；导则有 41 张表，表格不切对就等于没索引）
5. **语义滑窗**（按语义边界合并短块，保留重叠）
6. **QA-pair 切分**（从条款抽 QA 对直接建索引，`data/eval/qa_pairs.csv` 已是这个格式的输入）

PRD 要写清：每种策略的 chunk 元数据长什么样、表格块如何存表头、跨页段落如何合并、以及**用什么指标判定哪种策略更好**（见第 7 节）。

### 第 4 节 · 索引与检索架构
- **索引**：向量（嵌入模型 + 向量库）与 BM25 两路并行；说明选型与降级路径。
- **混合融合**：RRF（Reciprocal Rank Fusion），给出 k 值与公式。
- **过滤与排序的顺序**：**先过滤，再排序**（见 2.4），要写明向量侧 payload 过滤与 BM25 侧"过滤后子集重算"两处实现细节。
- **重排**：是否接 reranker。PRD 里要给出**明确结论**——如果不做，写清理由（本场景过滤后候选集已很小，重排收益有限），如果要做，写清模型与延迟代价。

### 第 5 节 · 版本治理与时点问答
- **时点模型**：每次请求显式传入 `query_time`（**不读系统时间**，保证可复现）；同时解析问题中的显式时间表达（如"2023 年那会儿""现行标准"），两者共同决定检索区间。
- **两种口径**：
  - `current`（默认）：检索区间为"至今仍生效"
  - `as_of(t)`：检索区间为"t 时刻生效的版本"
- **版本卡**：命中结果附一张版本卡（当前版本 + 生效日 + 废止关系 + 变动摘要）。
  → **硬约束：版本卡必须由代码强制拼接到答案下方，不能靠 prompt 让模型自觉说。**
  → **硬约束：过滤后过期 chunk 根本不进上下文，所以不存在"模型引用了过期条款然后我们提示它"这种情况。** PRD 里不要写成"命中过期版本时提示用户"——那描述的是一个我们没做的机制。
  → `as_of` 口径下，"废止"是一个有用的历史事实而非警告（例：问 2022 年适用旧版，旧版被新版权取代是正确答案的一部分）。

### 第 6 节 · 引用溯源
答案附条款级引用，每条引用可展开：原文块 + **页码** + **文档标题/文号** + **版本状态** + **来源 URL**。
要求写清：引用是**代码生成**的（从检索结果直接带出，不由模型生成），防止模型编造引用。

### 第 7 节 · 评测方案
这是 PRD 里最不能糊弄的一节。要求：

- **题集**：以 842 条候选为底，精修成正式题集。至少覆盖 5 种题型：
  1. **事实题**（规程怎么规定的）
  2. **数值题**（设计压力、氧含量限值、浓度限值——带保真锚点，比对数字而非字符串）
  3. **版本陷阱题**（问 2023 年答 2025 版 → 判错；问现行答已废止 → 判错）
  4. **拒答题**（语料里根本没有的设备/条款 → 必须拒答或要求澄清）
  5. **跨文档推理题**（同一台设备的规程要求 + 历史事故对比）
- **主指标**：
  - 检索层：**Recall@k / MRR**、**过期版本误召回率**（本项目最关键，应作为主指标之一）
  - 生成层：事实题的答案正确性、数值题的数值精确匹配率、拒答题的误答率
- **对比基线**（必须有，否则无法说明设计价值）：
  - B1：直接把语料塞给大模型问
  - B2：BM25 单路，不做版本过滤
  - B3：混合检索 + 版本过滤（本项目）
- **硬约束**：任何指标必须写明 **n（样本量）、分子、分母**；样本量小就明说置信区间宽、只报粗结论。**禁止在 PRD 里写没有实测支撑的目标数字。**

### 第 8 节 · 非目标与红线（必须显式列出）
这一节存在的意义是防止后续实现（或面试时的表述）超出实际范围。至少包含：
- 不做动态冲突检测与自动裁决（版本冲突降维成静态版本卡）
- 不做条款级有效期（只有文档级生效区间）
- 不做政策自动更新跟踪（语料是手动选取与入库的）
- 不做生产部署（单机演示）
- 不引入编排框架（链路固定，无动态分支；引入只让错误定位更难）
- 不使用受版权保护的厂商文档
- **OCR 只作为扫描件兜底链路，不是主路径**

### 第 9 节 · 里程碑与验收标准
按可验收的粒度拆（例如：切分策略对比实验完成 → 每种策略的 Recall@5 与 chunk 数产出成表；检索基线完成 → B1/B2/B3 三组数字落盘 `eval_runs/YYYYMMDD_HHMM.json`）。**每个里程碑都要有"怎么算做完"的客观标准。**

### 第 10 节 · 风险与应对
至少覆盖：
- 嵌入模型拉不下来（降级路径是什么，降级后哪些指标会受损）
- `extract_quality != ok` 的 7 份文档污染检索（应对策略）
- 语料只覆盖安全规程侧、缺厂商设备手册侧（真实缺口，不要粉饰）
- 评测集精修成本与人工标注一致性
- **证据链留存**：每次评测结果 JSON 带时间戳落盘不覆盖；建立失败样本记录（每条：现象 → 根因 → 下一步）；建立踩坑日志。**这一条决定了项目在面试追问时能不能拿出证据。**

## 五、写作与表述约束（PRD 成稿也必须遵守）

1. **凡是要写进 PRD 的数字，只能来自两类来源**：本文件第三节的已核实事实，或已完成的评测结果。**任何"预期可达 X% 准确率"这类话都不要写**——目标可以写成"以 Recall@5 与过期版本误召回率为准绳做策略选型"，而不是"准确率不低于 85%"。
2. **区分"已实现"与"计划"**。当前真实进度：语料与评测候选池已完成，chunk/索引/检索/生成/评测全部未开工。PRD 的语气应当诚实反映这个起点。
3. **不写"我们"，写"我"**（个人项目）。
4. **不发明不存在的行业术语和缩写**；中文术语第一次出现时给出全称与英文原文。
5. **算法要给出出处**：BM25、RRF、cosine 都是既有方法，写"采用"而非"设计了"。
6. **每个技术选择都要写"为什么选它"和"代价是什么"**，PRD 里的架构决策必须能被追问两层。
