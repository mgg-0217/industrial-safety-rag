## K-01 · 全角数字占了近两成，数值检索直接失效

**现象**：问「设计压力 0.35」召不回正文里的「０.３５」。全语料 26 份 md 里，
全角数字 4583 个、半角 23025 个中的其余部分 —— 全角占比 **19.8%**。

**根因**：PDF 文本层抽取出来的数字是全角的，几乎全部来自两份 PDF 导则
（AQ/T 3034 与《有限空间作业安全指导手册》）。典型样本：
导则封面 `２０２２Ｇ１０６０１发布`、作业票 `２０２２年 ４月 １日`。
HTML 源（政府网页）全是半角，所以问题只在 PDF 侧。

**解法**：`src/normalize.py::normalize_digits()` 把全角数字/字母/数值符号
（`０-９ Ａ-Ｚ ａ-ｚ ． ＋ ％ ＝ －`）转半角。**中文标点（，。；：、！？（）《》〔〕）
故意不转** —— 它们不承载数值，且转了会破坏原文可读性。

**验证**：归一化后全角数字 4583 → **0**。位号召回率 **0% → 100%**。

**耗时**：约 40 分钟（含统计脚本）。**教训**：脏数据要先统计再处理，别凭直觉。

## K-02 · 位号的破折号是全角的，且段数都不统一

**现象**：manifest 里位号记的是 `19-V-4215`（半角连字符），正文里写的却是
`19—V—4215`（全角破折号 U+2014）。不归一化则位号检索命中率 **0%**。

**根因**：PDF/网页抽取保留了原文的全角破折号。同一台设备在两批语料里
**连段数都不一样**：

| 文档 | 原文写法 | 段数 |
|---|---|---|
| `case_quanzhou_1220`（事故调查报告） | `19—V—4215` | 3 段 |
| `case_quanzhou_rectify_2026`（整改落实报告） | `19—V4215` | 2 段 |

**解法**：分两步。第一步把位号上下文里的破折号换成半角连字符
（`normalize_equipment_tags`，**上下文感知**：只有两侧是 ASCII 数字/字母
才换，中文破折号 `——` 一律不动 —— 全文 86 处 `——` 零误伤）。
第二步仍不够 —— 因为段数不同。追加第三轨 **canonical key**
（`tag_key()`：去分隔符 + 大写，`19—V—4215` 与 `19—V4215` 都压成 `19V4215`）。

**耗时**：约 50 分钟。**教训**：等价形态要压到同一个 key，不能停在"换字符"这一层。

## K-03 · `str.translate` 的表用字符串 key 会静默失效

**现象**：`normalize_digits()` 写完跑一下，全角数字一个没少（4581 → 4581）。
表里明明有 `'０' → '0'`，字典也构造对了。

**根因**：`str.translate()` 的翻译表以 **Unicode 码位**为 key。传一个
`{字符: 字符}` 的 dict 进去，查表永远查不到，**不报错、原样返回** ——
静默失效最难查。

**解法**：先经 `str.maketrans(_TRANSLATION)` 转成码位表再传。

**耗时**：约 15 分钟。**教训**：静默失效的 bug 必须靠"断言结果"抓，
靠读代码看不出来 —— 所以归一化模块配了 `tools/test_normalize.py` 自检脚本。

## K-04 · 正则自动抽位号，误抽率高到不可用

**现象**：写了个 `EQUIPMENT_TAG` 正则想从正文里自动抽设备位号，
在 26 份语料里抽出 **132 种**"位号"。逐个一看，绝大多数是别的东西：

```
2024-10-15（日期）      020-83137111（电话号码）   0551-62999504（传真）
GB30871-2022（标准号）   2025-00062（文号）          H2O2-C3H6O（化学式）
```

真位号（`19-V-4215` / `T-4200` / `1910-PV—42151` …）只占一小部分。

**根因**：工业文档里"短横线分隔的数字字母串"这个形态太常见，靠形态无法区分
位号和日期/电话/标准号。要区分就得靠上下文（是不是设备清单段），
那是 NER 的活，不是正则能干的。

**解法**：**放弃自动抽取，改用 manifest 的人工标注位号池**。
检索时拿标注位号去归一化文本里做精确匹配 —— 准确，且能定位到出现位置。
代价：manifest 目前只标注了 3 份文档的位号，未标注文档的位号检索不到。
补标注是人工成本，优先级低于先把检索链路跑通。

**耗时**：约 30 分钟。**教训**：能人工标注的别用正则猜。自动抽取不是免费的。

## K-05 · `equipment_tags` 字段名和它装的不是一回事

**现象**：做位号自检时发现，manifest 的 `equipment_tags` 里 29 个标注中，
**只有 6 个是位号形态，23 个是中文设备类别名**：

```
锅炉、压力容器、起重机械、电梯、游乐设施、厂内机动车辆、
加油机、油罐车、卸油管、油气回收装置、轨道球阀、有机热载体锅炉 …
```

**根因**：这个字段在建库时被理解成"设备相关标注"，实际混了两类语义：

| 类型 | 例 | 检索行为 |
|---|---|---|
| **位号**（原文锚点） | `19-V-4215`、`T-4200` | 必须在正文里定位到，用于溯源与跨文档关联 |
| **类别名**（分类标签） | `锅炉`、`压力容器` | 用于**过滤**（"所有讲锅炉的文档"），不要求在原文出现 |

两者混在一个字段里，检索时必然要分开处理，却没法靠字段名区分。

**解法**（**待 PRD 裁决**）：拆成 `equipment_type`（类别）+ `equipment_id`（位号），
或改名为语义中性的 `equipment_names`。代码里已用 `is_equipment_tag()`
按形态区分，暂不依赖字段名。

**耗时**：约 20 分钟。**教训**：schema 的字段名要有明确语义边界，混装是隐患。

## K-06 · 政府网页用嵌套 div，正则抽正文会被第一层 `</div>` 截断

**现象**：海阳市场监管局那个页面，HTML 有 139KB，正则抽出来只有 466 字。

**根因**：政府页面普遍是 `<div><div><div>正文</div></div></div>` 结构，
非贪婪正则匹配到第一层 `</div>` 就停了。

**解法**（建库阶段已做）：`tools/html_to_md.py` 用**标签配对提取**
（`extract_balanced`），并加**正文区间兜底** —— 容器提取不足 1200 字时，
回退到全文清洗 + 标题/尾部标记定位。

**遗留**：安徽、海阳两个页面正文是**图片版**，仍需 OCR（`extract_quality=partial`）；
淮安页面 URL 已失效（`extract_quality=failed`），内容由应急管理部官方 PDF 覆盖。

## K-08 · 候选题干的根因不是「少字」，是 `clause_no` 被当正文切片

**现象**：普查 842 条候选，142 条题干被抽取截断，117 条短于 30 字符，
26 条缺字。看起来像"抽取时把字吞了"。

**根因（实测确认）**：候选生成模板是
「《文档名》中，{`clause_no` 切片}是怎么规定的？」，
而 `clause_no` 是切条款时取标题的**前若干字符**，切点落在词中间：

| 实际题干 | `clause_no` 原文 | 问题 |
|---|---|---|
| `《…》中，擅自离开是怎么规定的？` | `2.3.3作业期间不得擅自离开，全过程掌握作业者…` | 丢掉整条编号与前半句 |
| `《…》中，“先通风是怎么规定的？` | `3.1按照”先通风、再检测、后作业”的原则…` | 引号切在中间，不成句 |
| `器主装置的限值是多少？` | `（五）主要装置的限值…` | 主语残缺 |

**量级**：**576/842（68%）** 的题干带这个毛病（`clause_derived_question`）。

**解法**：这类题**补字修不好**，必须让 LLM 读 `gold_answer` 全文重新组织问法。
所以 M2 第二步是"重写"而不是"修补"。

**教训**：指标异常时先查**生成逻辑**，不要先查数据。题干截断是症状，
模板切片才是病因——在候选生成器里查比在 842 条数据里查快得多。

## K-09 · 标记表用 `qid` 做 key → 重复 id 互相覆盖，静默漏标记

**现象**：普查脚本第一版统计 `missing_key_points` 命中 **835** 条，
但候选池是 **842** 条，差 7 条。

**根因**：`flags` 用 `qid` 做 dict key，而候选池有 **7 个重复 qid**
（`qid = doc_id__clause_no` 拼接，同 doc 下 `clause_no` 重复即撞）。
后写入的行覆盖了前一行，**前 7 行的标记全部丢失**。

**解法**：标记按**行索引**存，不用 `qid` 做 key。

**教训**：⚠️ **差值正好等于重复 id 数**是个强信号。
任何"统计数比预期少 N 条"的现象，先怀疑 key 唯一性。
另一个信号：`needs_human_review` 也是 835 —— 所有标记同时少 7，
说明是**结构性覆盖**而非某条检查的逻辑错误。

## K-10 · 抽样要「真轮转」：按文档顺序取光会漏掉 5/15 份文档

**现象**：首批抽样 180 条事实题，只覆盖 **10/15** 份文档，
`mem_2019_78` 一家吃掉 67 条。

**根因**：抽样代码按文档名排序遍历，每份文档把额度吃到接近饱和才换下一份。

**解法**：真轮转——每轮从每份文档各取 1 条，文档内按"问题严重度"优先。
改完覆盖 **15/15** 份文档，分布从 67:1 变成 26:26:18:18:17:17:17:17:16:13:12:12:6:3:1。

**教训**：覆盖度要**单独断言**（`覆盖文档 N 份 / 总 M 份`），
不能靠肉眼看分布表。分布表看着"挺均匀"的时候，可能已经漏了一半文档。

## K-11 · 策略 6 的 QA 切分：排除的单位是**条款**，不是题

**现象**：按"把 842 条对半切"实现，索引侧 835 条、评测侧 7 条，
同 `(doc_id, clause_no)` 交集 **7** 组 —— 违反 PRD 的硬约束。

**根因**：842 条分 **835 个条款**，其中 **828 个条款只有 1 条题**。
按题对半切必然有一半条款两侧都有。
而且切分的**顺序**错了：QA 索引是按 **条款**泄漏的（同条款的题问同一件事），
所以必须「**先定评测集用到哪些条款，再把这些条款的题排除出索引**」，
而不是「把候选池对半切」。

**解法**：以 `test_set.jsonl` 的 `(doc_id, clause_no)` 集合为准绳，
凡被评测集占用的条款，其题一律不进索引侧。

**代价（写进报告）**：索引规模由「被评测集占用的条款数」决定，不是候选池的一半。
PRD 3.1 里"索引规模只有候选池的一半"只在"条款与题一一对应"时成立。

**教训**：策略 6 的硬约束是「检索库中不允许出现与评测题 `clause_no` 相同的 chunk」，
这是**条款级**约束。约束的粒度决定切分的粒度——按更细的粒度切，满足不了它。

## K-12 · 位号验证必须压缩分隔符——否则"验证通过"是假的

**现象**：验证假位号 `T-9001` 不在语料里，两个口径都是 0 命中，
看着挺安全。但真位号 `19-V-4215` 的出现次数也是 **0**，
而它明明在事故报告里出现了 34 次。

**根因**：`tag_key()` 去掉分隔符（`19-V-4215` → `19V4215`），
但 `norm_text` **保留**分隔符（还是 `19-V-4215`）。
拿 key 去 count 归一化文本，永远是 0——**只查了一半形态**。

**解法**：与 `normalize.find_tag_occurrences` 对齐——把待查文本也压成
无分隔符形态再比（`squash()`），原文侧还要先跑一遍 normalize
把中文破折号 `—` 转成半角 `-`。

**修正后**：`19-V-4215` raw=34 / norm=34、`1910-PV-42151` 14、
`T-4200` 12、`T-4300` 6、`MP-41009-200-S1B-H1` 1。
真位号**恰好 5 个**，与 PRD 7.1 的事实一致；其余 14 个是设备类别名。

**教训**：验证脚本本身也要被验证。**拿一个已知存在的对象去跑验证器**，
看它能不能查到——查不到就是验证器坏了，不是数据不存在。
（这跟"单元测试要先写一个必然失败的用例"是同一回事。）

## K-13 · 质检判据查错了字段 → 61 条被误判成「key_point 不可达」

**现象**：M2 合成三类题后跑质检，`key_point 不可达` 命中 **60 条**：
版本陷阱题 41 + 跨文档推理题 15 + 数值题 4。看起来像"LLM 造的题全是幻觉"。

**根因（实测确认）**：判据是「key_point 能否在 `gold_answer` 里找到」，
而这三种题的 `gold_answer` 本来就不是它该在的地方：

| 题型 | `gold_answer` 是什么 | 判据查它 → 结果 |
|---|---|---|
| 版本陷阱题 | `None`（答案在 `expect_doc_id` 指向的文档正文里） | 永远找不到 |
| 跨文档推理题 | LLM 的**概括**（不是原文片段） | 字面包含必然不成立 |
| 数值题 | 原文切片，但 `key_points` 是**保真锚点**（数值） | 锚点格式与原文写法不一致 |

**解法**：把"对齐源"按题型分开，抽成 `src/eval_align.py`，
质检与规范化**共用同一套** `alignment_source()`：

| 题型 | 对齐源 |
|---|---|
| 数值题 | `must_include_numbers`（锚点本身）；可达性判定查 `gold_answer` |
| 事实题 | `gold_answer` |
| 版本陷阱题 | `expect_doc_id` 对应文档的 md 正文 |
| 跨文档推理题 | `expect_doc_id` + `related_doc_ids` 的 md 正文 |
| 拒答题 | **无** —— key_point 是判分标准（「是否声明查不到」），不是原文断言 |

拒答题那一行是最容易漏的：它的正确答案就是「语料里没有」，
**压根不指向任何原文**，要求它字面可达是逻辑错误。这类题单独标
`key_point_source = "refusal_criteria"`，质检时跳过可达性判据。

**修正结果**：不可达 60 → **4**，无标记率 72% → **91.5%**（280/306）。

**教训**：⚠️ **"数据有问题"和"判据用错字段"在报告里长得一模一样**。
本例里两者的修复动作完全相反（一个要重造数据，一个要改判据），
而当时差点按"重造"处理。
**判据本身要先自证**：拿一条**已知应该通过**的样本跑一遍判据，
过不了就是判据坏了。这个顺序和 K-12 的"拿已知存在的对象去验证验证器"是同一条。

## K-14 · 只按 `clause_no` 切分不够：不同条款会产出**字面相同**的题干

**现象**：策略 6 的 qa_split 跑完，`(doc_id, clause_no)` 交集 = 0 ✅，
但**同 question 交集 = 5 条** —— 同一道题同时在索引侧和评测侧，
命中即判评测无效（比 clause 泄漏更严重）。

**根因**：题干模板是「《文档名》中，{条款语义短语}是怎么规定的？」，
短语从条款里截。**相邻条款常共享同一短语**，于是题干一字不差：

| 条款 | 截出的短语 | 题干 |
|---|---|---|
| `1.控制方案变更应办理审批手续；` | 办理审批手续 | 《…导则》中，办理审批手续是怎么规定的？ |
| `2.实施特殊作业前，必须办理审批手续。` | 办理审批手续 | **同上，一字不差** |

**解法**：切分后再加一道**题干级**去重 —— 索引侧里凡是题干与评测侧重复的
一律剔出（数据不丢，评测侧本来就有一条同样的题）；
索引侧**内部**同题干重复也剔（索引里有两条一样的 QA，命中会被算成两个证据，
等于白送召回）。实测剔掉 6 + 22 条，两侧交集双双为 0。

**教训**：**不相交要按"检索时能匹配上的那个单位"来判，不是按你脑子里那个单位**。
条款是切分单位，但**用户输入的匹配单位是题干**。
只验条款交集会漏掉题干级泄漏 —— 单元格里没有任何一处会告诉你漏了。

## K-15 · 产物必须累积：每次从原始数据重算 = 静默覆盖前一步的成果

**现象**：`rewrite` 阶段跑完后，`qa_pairs_rewritten.csv` 里 842 条
`question_rewritten` **全是空的** —— `backfill` 阶段回填的 198 条没了。

**根因**：`rewrite` 读的是**原始** `qa_pairs.csv`，写的时候整个覆盖产物文件。
`backfill` 的结果只活在产物文件里，没进原始文件，于是被抹掉。

**解法**：读原始 + **以产物为准回填**已改写部分；行序对齐（qid 有 7 组重复，
按 qid 建索引会撞）。实测重跑 backfill 后 198 条回来了。

**教训**：**流水线里凡是"读 A 写 B，A≠B"的地方，B 都不能是唯一副本**。
这次是"中间结果只写在输出文件里"这个经典问题。
判据很简单：**任何一步的输入，都应该包含上一步的输出**。

## K-16 · 对齐后的 key_point 可能互相包含 → `key_point_coverage` 的分母被灌水

**现象**：某条版本陷阱题的两个 key_point 是
`所有动火作业时应配备能够采集全过程作业影像的防爆型摄录设备`
和 `所有动火作业时应配备能够采集全过程作业影`
—— 后者是前者被削掉尾巴的残片。判分时命中一个就等于命中两个，
`key_point_coverage` 的分母里有一项是**零信息量的重复项**，分数虚高。

**根因**：对齐用的「最长公共子串」按段落切，
不同段落可能切出**高度重叠**的片段；两条 kp 各自对齐后撞到同一句话。

**解法**：对齐后加一道 `dedup_key_points()` —— 归一化后互为子串（或一方是另一方的
子串且 ≥ 8 字）的只留信息量大的那个。实测**去掉 206 个重复 kp**（306 条题），
去重后分布正常：2 个 kp 136 条 / 1 个 95 条 / 3 个 52 条 / 4 个 22 条。

**附带修掉的一个 bug**：`best_span()` 原来按「长度比例」把归一化串的坐标换算回原串，
实测会**偏移**，切出末尾被削掉的片段。
而下游的字面包含判定**本来就在归一化串上做** —— 换算回原串既无必要也不准。
改成直接在归一化串上取片段，偏移消失。

**教训**：⚠️ **"每个 key_point 都可达"不等于"key_point 列表有效"**。
可达性只保证每一项在原文里找得到，不保证各项**互不重复**。
指标的**分母**会被灌水这类问题吃掉，而可达性检查一点都查不出来 ——
它俩是两个正交的检查，必须都做。

**另一个要记住的副作用**：对齐后的 key_point 是**归一化形态**（全角逗号变半角）。
这是自洽的（判定用同一套归一化），但人工核对时看到的 kp 与原文标点不完全一致，
别误判成"原文里没有这句话"。

## K-17 · 🔴 PDF 抽取层把正文拆散了 —— 而 PDF 本身完全正常

**现象**：`AQ_T3034_2022_huagong_anquan.md`（项目里最大的一份，59 页 41 表）
的正文读不通，条款号 `4.1.2` 被撕成两行：

```

．． “ 、 ” ,
目标 安全发展战略 安全使命精神等为内容的安全生产核心价值观 构建符合企业安全生产特点的良
```

**根因**：**在 PDF 里，不在抽取代码里，也不是 pdfplumber 的 bug**。
该 PDF 的中文与 ASCII 用两套字体，两套字体的 ascent/descent 不一致 →
pdfplumber 用**字体度量**算出的 char bbox 整体错位 **8.5pt**。
它默认 `y_tolerance=3`，只把 `top` 相差 ≤3pt 的字符算同一行 → 同一视觉行被拆成 3–4 条"行"。

| 行 | pdfplumber 的 `top` | **真实基线** |
|---|---|---|
| 中文正文 | 132.30 | **702.65** |
| 条款号数字 | 133.90 | **701.39** |
| 标点 | 139.30 | **702.94** |
| 条款号句点 + `GB/T37243` | 140.90 | **701.39** |

按 `top` 分行 → 4 行；按基线分行 → **1 行**（跨度 1.55pt，真实行距 15.91pt）。

**解法**：`src/pdf_lines.py` —— 按文本矩阵基线归并成行、行内按 `x0` 排序。
关键在于错位出去的 run **x 坐标仍在原位**（`．．．` 在 x=76.5、
`GBT３７２４３` 在 x=408，正好在"按照"与"的要求"之间），按 x 重排就还原了阅读顺序。

**验证**：`tools/validate_rebuild_vs_ocr.py` —— 渲染页 → rapidocr → 比字符相似度。
OCR 只看像素，不经过 pdfplumber 任何逻辑，是独立裁判。实测平均 **0.8300 → 0.8908**，
**每页持平或更好，零回退**。容差用 `tools/sweep_baseline_tol.py` 扫出来：
2.0–4.0 同分（0.8908），取 3.0。

**耗时**：约 4 小时（含诊断、根因定位、验证、扫参）。**教训**：
**"抽取结果读不通"要先分清是 PDF 的锅还是抽取器的锅** ——
本次先渲染成 300dpi 位图逐行核对，确认版式是对的，才敢动抽取层。
另外，**判据要跟着语料长**：`CLAUSE_RE` 要求半角 `\d+[\.、]`，
而 PDF 字体把条款号映射成全角 → 全角归一化不做，这��文档永远 0 候选。

## K-18 · 用 OCR 当独立裁判，别用自己的输出验证自己的输出

**现象**：修完抽取层，怎么证明"改好了"？如果拿新抽取结果跟旧抽取结果比，
那是**自己验自己** —— 两边都错了也一样"一致"。

**根因**：改前改后都是 pdfplumber 出的，比出来的差异只反映"我改了哪几行"，
不反映"对不对"。

**解法**：引入**完全独立**的信号 —— 把页渲染成位图，用 rapidocr 识别，
拿 OCR 结果当"页面真实内容"，比字符相似度。OCR 只看像素。

顺带踩到两个坑：
1. **整页 OCR 检测不到任何文字**。rapidocr 的检测默认
   `limit_side_len=736, limit_type='min'`，A4 整页（200dpi ≈ 1654×2339）
   被缩到 736 宽，10pt 的字只剩 3px → `dt_boxes is None`。
   **必须按横向条带切**（700px 一条、留 60px 重叠）再 OCR。
2. **残留差距不要当成 bug**。修完相似度 0.89 而不是 1.00，
   逐条 diff 剩下的全是 OCR 自己的错（`T江` vs `工工`、`（0` vs `G`）、
   全角半角标点差异、以及**水印被 OCR 认了出来**（水印是矢量图形，不是文本）。

**耗时**：约 1 小时。**教训**：**验证信号的独立性比验证本身更重要** ——
拿同源的输出验同源的输出，等于没验。

## K-19 · 🔴 策略 4 的表头整个丢了 —— 第一条数据行被当成了表头

**现象**：`data/chunks/table.jsonl` 里表格 chunk 的 `table.header` 是
`['地下 有限空间', '废井、地坑、地窖、通信井', '缺氧、高处坠落']` ——
但表格的真实表头是
`['有限空间 种类', '有限空间', '作业可能存在的主要安全风险']`。
chunk 的 `text` 开头也是那条数据行。

**根因**：`parse_table()` 返回 `(数据行, 表头)`，但 `_scan_blocks()` 只把
**数据行**存进 `b.rows`，表头只用来做了个布尔判断就丢弃；
而 `strategy4_table()` 又用 `rows[0]`（也就是第一条**数据行**）当表头，
并把 `rows[1:]` 当数据 —— 于是真表头彻底消失，第一条数据行被重复了一遍。

**解法**：`Block` 增加 `header` 字段，表头与数据行**分开存**；
策略 4 用 `b.header` 而不是 `rows[0]`。

**后果**：PRD 3.1 策略 4 明写「表头行原样存进 chunk 的 `text` 开头（不是只存 metadata）…
行级答案（"导线型号"）必须带表头才成立」—— 这条**从来没做到过**。
PRD 3.3 还规定「表格切分策略的关键战场是数值题分项召回」，
表头丢了，表格类问题基本不可能召回对。

**耗时**：约 1 小时（写单元测试时发现）。**教训**：
**PRD 里写了不等于代码做了** —— 逐条对照验收标准，
每一条都要有一个能跑的断言兜底。

## K-20 · 🔴 折行表被误判成键值对表 —— 策略 4 在最表格密集的文档上一张表都不切

**现象**：`mem_2019_78_zhimengdaoze` 的 17 张排查表
（`序号|排查内容|排查依据`，每张 50–76 行、每表 1000+ 行）
全部被判成"键值对表" → 整表一个 chunk → **策略 4 完全没在工作**。

**根因**：旧判据是「非空格占比低 + 各行非空格数差异大」。
但 **PDF 表格的单元格内容会跨行折行**，pdfplumber 把一个逻辑行
拆成多条物理行：

```
|  | 1.较高浓度环氧乙烷设备的安全阀前应设爆破片，爆破 |  |
|  | 片入口管道应设氮封，且安全阀的出口管道应充氮； | 《石油化工企业设计防火标准（2018版》 |
| 7 |  |  |
```

于是每行只剩 1–3 个非空格 → 占比 0.40–0.49、差异 2 → 命中旧判据。
**折行是抽取产物，不是表格的性质** —— 判据把它当成了性质。

**解法**：改判据为**行内内容横向散成多段**（"标签 空 空 值" → ≥2 段连续非空）。
折行表的内容集中在**相邻**列（1 段），键值对表散在**不相邻**的列（≥2 段）。
实测：排查表 1 段（数据表）、作业票 3–4 段（表单）、`gaoqing` 2–3 段（表单）。

**修复后**：`mem_2019_78` 的真表头 14 → **35**（全部正确），键值对 17 → **0**。

**耗时**：约 1.5 小时。**教训**：
**判据要选"反映性质"的信号，不要选"反映抽取产物"的信号** ——
"非空格占比低"既可能是表单的性质，也可能是折行的产物，两者撞在一起时，
只有**能区分二者的信号**（横向分布）才是对的。

## K-21 · 🔴 归一化把 HTML 注释压掉 —— 51 个页码锚点整片消失

**现象**：候选池重建后，**每一条候选的 `page_no` 都变成了 None**
（修复前 362 条带页码锚点）。

**根因**：`src/normalize.py` 的位号归一化里有一条
`_MULTI_DASH = re.compile(r"-{2,}")` → 把连续两个连字符压成一个。
它的本意是处理位号 `19——V`，但**没有上下文约束**，
于是 HTML 注释 `<!-- page:12 -->` 里的 `<!--` 和 `-->` 各含两个连字符，
被压成 `<!-` 和 `->` → **页码标记没了**。

**解法**：给规则加上字母数字上下文
（`(?<=[0-9A-Za-z])-{2,}(?=[0-9A-Za-z])`）——
`19——V` 两侧是字母数字，仍然压；`<!--` 前面是 `!`，不匹配。

**耗时**：约 20 分钟。**教训**：
**"归一化"这个动作本身会破坏别的结构** ——
这次破坏的是 HTML 注释，而注释里装的是页码锚点。
凡是要做全局文本替换的地方，先问一句"什么结构会被误伤"。

## K-23 · 🔴 按行序对齐，在候选池重建后把题干安到了别的行上

## K-24 · 上标被基线错位截断 —— `100m³` 变成 `100m`

**现象**：基线重建修好了行序，却把 `100m³` 截成 `100m`（上标的 `3` 跑到别的行去了）。

**根因**：上标 `3` 在 PDF 里是**另一个字号**（实测 6.96 vs 正文 10.56 = 0.66×），
基线也**更高**（偏移 5.03pt）—— 比行内字体错位（1.5–1.6pt）大得多，
基线容差根本兜不住。

**解法**：聚类后加一道**小字号并带**规则 ——
邻接两带里字号明显小的那带（≤ 主带的 0.8 倍），
且基线距离 ≤ 主带字号的 0.6 倍 → 并入主带。

**为什么用"字号"当主判据而不是"基线距离"**：
纯基线距离分不清上标和"表格相邻行"（距离可能一样）；
而**字号是排版意图的直接证据** —— 上标必然用更小的字号，
表格相邻行是同字号的。表格里整行小字也不会被误并（两带字号相同，比值 1.0）。

**教训**：**修好一个错，别换来另一个错** ——
这类"位置/尺寸"信号往往是多维的，只盯一维会顾此失彼。
实测同一批文档：化学式从 `H S`+孤立的 `2` 变成完整的 `H2S`。

**根因**（两层）：
1. `build_skeleton` 按标题拆块时**新建 Block 对象**，只传了 `page_no`；
   而跨页合并过的块 `page_no` 是 None、页码只存在 `pages` 里 → **页码整个丢掉**。
2. 修好第 1 点后，子块继承**父块**的 `pages` → 一个跨页块被拆成 5 个子块，
   5 个子块全被标成"跨页"，但其中几个的内容其实全在第 N 页 → **假阳性**。

**解法**：Block 增加**行级页码** `line_pages`，子块按**行**算自己的 `pages`。
修后：策略 2/3 跨页 120、策略 5 跨页 75（真实值，与 174 个页边界相符）。

**教训**：**"父对象的元数据"不能直接下传给子对象** ——
父对象携带的是**聚合**信息（它跨了几页），子对象携带的是**归属**信息。
聚合信息下传 = 假阳性；归属信息不下传 = 漏报。

## K-33 · 🔴 "不可评"的题**只在开了版本过滤的配置下才被排除** —— B2 被人为压低

**现象**：策略 4（表格切分）在 B2（不过滤）下 R@5 = **0.077**，
在同一套题上换 B2′（过滤）却是 0.500 —— 但两组的**可评题数**也不一样（78 vs 12）。
数字对不上，是判据的问题。

**根因**：`gold_evaluable()` 原来长这样：

```python
if g.kind == "none": return False
if alive_set is None: return True      # ← B2 走这里，直接放行
...
```

**"gold 集合为空"（该策略根本没索引这份文档）这一支没有判**：
- 过滤模式下，后面的 `any(i in alive_set ...)` 顺带把它判成不可评 → **被排除**；
- 不过滤模式下（`alive_set is None`）**提前 return True** → 被当成"可评"，
  而它的 gold 集合是空的 → `hit_and_rank` 永远返回未命中 → **算成漏召**。

**影响**：同一道题在两组基线里**待遇不同** → B2 被系统性压低
（策略 4 的 B2 实际应是 0.500，被压到 0.077）。
这类偏差会直接误导"版本过滤有没有用"的判断。

**解法**：判据拆成三态并**在所有基线配置里一致对待**：
`none`（无 gold）/ `absent`（gold 不在候选集 —— 该策略没索引这份文档）/ `filtered`（被版本过滤掉）；
后两者都**不计分**，但**分开计数**（`n_gold_absent` / `n_gold_filtered`），
因为"数据里没有"和"被规则滤掉了"是两种完全不同的原因。

**教训**：🔴 **"不可评"是评测口径里最容易只写一半的东西** ——
它在"有过滤"和"无过滤"两条路径上各走一次，只要有一条漏判，
两组基线就不可比。**判据要按"原因"分类，而不是按"返回 True/False"分类**，
并且**每种原因都要单独计数**，报告里才看得出问题出在哪。

## K-34 · 🔴 六种切分策略的"共同子集"是**空集** —— 专用策略的分母根本不是同一批题

## K-35 · 🔴 `key_point` 的"字面可达"取决于**匹配口径** —— 直接字面匹配会漏判 55%

**现象**：M5 准备生成层指标时顺手验一下 `key_point` 能不能在原文里找到 ——
**只有 240/534（45%）逐字命中**。但质检报告里这些 key_point 都标着"已对齐回原文"。

**根因**：**"对齐"和"可达"用的是两套文本**。
- key_point 是用 `N.normalize()`（数字全角→半角、位号破折号→连字符）处理过的；
- 证据文本也是 `N.normalize()` 过的，**但没有做标点折叠**；
- 于是 `'处理建议:由泉港石化'`（半角冒号）匹配不上原文的 `'处理建议：由泉港石化'`（全角）；
  `'0.1 MPa'`（数与单位之间有空格）匹配不上原文的 `'0.1MPa'`。

实测三档口径：

| 匹配口径 | 命中率 |
|---|---|
| 逐字匹配 | 240/534 = **45%** |
| 去空白 + 逐字 | 324/534 = 61% |
| 标点折叠 + 去空白 + 小写 | 448/534 = **84%** |

剩下 16% 里，**84 条是拒答题的判分标准**（"明确表示语料中无该设备的相关规定"）——
🔴 **它们本来就不该指向原文**（K-13 已记过：拒答题的 key_point 是判分标准，不是原文锚点），
把它们拿去和原文做字面比对是**逻辑错误**。

**解法（生成层开工前必须先定）**：① 定一个**"匹配用归一化"**（与检索用的 `norm_text` 分开）：
标点折叠 + 去空白 + 小写；② 拒答题的判分标准与原文锚点**分开判**，不共用一套匹配。

**教训**：🔴 **"可达"这个词必须绑定一个具体口径** ——
"逐字可达"和"归一化后可达"能差 40 个百分点。
凡是写"已对齐回原文"的指标，都要写清楚**对齐到哪一套文本**；
否则同一批数据，换个匹配函数，指标能差一半，而且两边都觉得自己没错。

## K-36 · 🔴 「肯定句 / 否定句」的判定写反了 —— `any(nm not in s)` 几乎恒真

**现象**：拒答判定（PRD 7.1）的第 3 步要判断"具体条款号/数值是不是只出现在否定句里"，
我写成：

```python
if any(nm not in s for nm in _NEG_MARKERS) and (_CLAUSE_RE.search(s) or _NUMBER_RE.search(s)):
    return ("manual", ...)
```

**根因**：`any(nm not in s ...)` 的意思是"**存在某个**否定标记**不在这句里**"——
句子只可能包含少数几个否定标记（未/没有/无/查不到…），所以这个条件**几乎恒真**，
于是**每句都被判成肯定句** → 所有"表态拒答但句子里有数字"的题都被推成"人工复核"。

正确写法是"句子里**没有**任何否定标记"：

```python
negated = any(nm in s for nm in _NEG_MARKERS)
if not negated and (...):
```

**症状**：单元测试 `test_refusal_pass_cases` 直接红 ——
"未找到 T-9001 的相关规定，语料中没有该设备。"被判成 mixed。
（如果没有单测，这个 bug 会一路跑到评测报告里：拒答误答率看起来"异常地高"，
因为所有通过的题都被算成了人工复核。）

**教训**：🔴 **`any(x not in s)` 和 `not any(x in s)` 差一个否定，语义完全相反**，
而 `any(x not in s)` 几乎恒真 —— **这类条件写出来要立刻问"它在什么情况下为假"**。
更一般的教训：**判定表里凡是"混合 / 边界"的情形，都要有一条单测专门喂它**，
否则默认分支会吃掉所有样本。

## K-39 · 🔴 拒答判分把**正确的拒答**判成误答 —— 误答率虚高到 1.0

**现象**：生成层冒烟跑 2 条拒答题，`refusal_verdict` 两条都是 `false_answer`。
但把模型原话读出来，两条都是**教科书级的正确拒答**：

> 「结论：资料中**未找到设备 T-9001 的具体检修周期**、作业前准备及检维修许可要求**；
> 也未说明该设备属于重点检修项目**……因此，**不能**据现有资料确定 T-9001 的具体执行要求。
> 一般性要求如下：……**若 T-9001 检维修涉及受限空间等特殊作业，还应执行相应特殊作业安全规范**」

**根因**：`scoring.refusal_judgement` 的第 1 步是
"主体（假位号）出现在**肯定句**里 → 误答"，
而"肯定句"的判据是"该句**不含枚举出来的 12 个否定词**"
（未/没有/无/查不到/未见/缺乏/不适用/非/尚未/并无/非本/找不到）。

🔴 **枚举否定词是死路** —— 模型实际会写的说法比枚举表长得多：

| 模型的真实写法 | 枚举表里有吗 |
|---|---|
| 「但**未给出** T-9001 的具体检修周期」 | ❌ |
| 「因此，**不能**据现有资料确定 T-9001 的要求」 | ❌ |
| 「**语料中无** T-9001 的相关规定」（"无"后还隔了空格） | ❌ |
| 「**若** T-9001 涉及受限空间…还应执行…」（这是"带明确限定"地引用通用条款） | ❌ |

这四句都提到主体、都没有表里的词 → 全部当成"给主体下了规定" → **误答**。

**这个 bug 最坏的地方**：它**不报错、不崩溃**，只是安静地给出另一组数字。
报表上看到"拒答误答率 1.0"，结论会是"模型完全不会拒答"，
而真实原因是**判分器写错了**。两个错误的修复动作完全相反
（一个是调模型，一个是调判分器），所以必须先分清。

**解法**（三条一起改，缺一不可）：

1. **否定标记改成正则覆盖词族**：`未/没有/无 + 动词`，外加条件词（若/如果/假如/倘若）。
   PRD 7.1 表格第 2 行的"带明确限定"就落在条件词上。
2. **句级否定与全文级表态必须用两套口径**：
   - 句级（"这句是不是在下规定"）用**宽**口径：句里出现"未/无/没有"就算在讲缺失；
   - 全文级（"模型有没有表态拒答"）用**严**口径：否定词与动词必须**挨着**出现。
   - 混用的后果：宽口径让"未表态"永远判不出来
     → PRD 表格第 4 行（"未表态，却给出别处条款"）漏判；
     严口径让"其他内容未提及"这种顺口一提也算表态 → 同样漏判。
3. **限定范围的表态单独抠掉**：
   「设备检修应按第三条执行，周期 30 天，**其他内容未提及**。」
   模型**根本没回答 T-9001**，它拿相邻条款冒充 ——
   这是 PRD 明确点名的有害行为（"模型绕过主题回答一个相邻问题，
   在检修场景里和编造一样有害"），不能因为句尾有个"未提及"就算它表态了。

**顺带修掉的**：`_NUMBER_RE` 原来单位是可选的 → 任何数字都算"具体数值"，
于是位号 `T-9001` 里的 "9001" 和列表序号 "1." 都算数 →
正确拒答被推进"人工复核"分支。现在**裸数字不算**，要么小数、要么带单位。

**回归**：新增 4 条单测（`tools/test_version_card.py`）：
`test_refusal_correct_answers_not_misjudged_as_false` /
`test_refusal_still_catches_fabrication`（放宽判定最怕"把误报修成漏报"，
所以正反两组必须同时锁住）/
`test_refusal_number_inside_tag_is_not_content` /
`test_refusal_dodging_answer_is_false_answer`。
全部 87 条单测通过。

**教训**：🔴 **判分器本身要被当成被测对象来测**。
对着手写的"标准答案"跑一遍不算数 ——
每条判分规则改动，都要用 `eval_runs/` 里**真实运行的模型输出**做回归。
判分器和被测系统用同一批文本过一遍，才能发现"规则写错了"这种
**不报错、只改数字**的问题。

## K-40 · 🔴 时间戳只精确到分钟 → 同分钟跑两批题，**后一批静默覆盖前一批的产物**

**现象**：用 `for` 循环按题型跑 5 批冒烟（每批一次 `run_generation_eval.py`），
5 批全部正常退出、全部有输出，但落盘只剩 **2 个** 文件：
`20261104_0942_generation_retrieval.json` 和 `20261104_0943_generation_retrieval.json`，
而 0943 那个文件里装的是**第 4 批**（跨文档推理题）的结果 ——
第 2 批（事实题）、第 3 批（拒答题）的产物**整个没了**。

**根因**：`ts = datetime.now().strftime("%Y%m%d_%H%M")` ——
**只有分钟，没有秒**。文件名 = `{ts}_generation_{cfg}.json`。
5 批里有 3 批落在同一分钟 → **文件名完全相同** → `write_text` 直接覆盖。
`--tag` 参数虽然定义了却**根本没进文件名**（PRD 7.5 要求 `YYYYMMDD_HHMM_<tag>.json`），
所以也没法靠 tag 区分。

**为什么这条特别阴**：
- 文件名完全合法、程序不报错、退出码 0；
- 被覆盖的那批**看起来**像是"没跑"或"没产出"，
  但实际上它跑完了、结果算完了、只是被写在别人的文件名下；
- 目录里文件数量对不上，很容易被误判成"脚本没写文件"而去查写入逻辑 ——
  而写入逻辑完全正常。

**解法**：
1. 文件名里**真的带上 tag 与题型筛选**（`--tag` / `--only-type` 一起进 stem）；
2. 落盘前过一遍 `_unique_path()`：目标存在就加 `-2`/`-3` 后缀 ——
   PRD 7.5 的"带时间戳、不覆盖"要靠**这个检查**保证，不是靠时间戳"够长"；
3. 顺手把逐题明细改成**边跑边落**（每条 flush），
   跑到一半崩了也留下已完成的部分 ——
   攒在内存里最后一次性写 = 全丢。

**教训**：🔴 **"不覆盖"必须由代码检查，不能靠命名约定的自觉**。
时间戳精确到分钟在"一天跑一次"的场景下看不出问题，
一旦**按题型分批跑**（这恰恰是评测集的正确跑法）就会撞。
凡是"产物不可覆盖"的承诺，都要有一条**显式的存在性检查**兜底。

## K-41 · 🔴 闭卷基线沿用了主配置的提示词 → 基线被自己的提示词**废掉**

**现象**：跑闭卷基线（B1a）时，模型的回答**每一题**都是：

> 「未找到相关规定。当前提供的资料片段中没有包含"两份榆林制度"的具体内容，
> 因此无法确定首次进入受限空间前的气体分析要求……」

4 道跨文档推理题，**4 道全是拒答**，一道都没答。

**根因**：主配置的系统提示词是

> 「你只能依据用户给出的【资料片段】回答问题……如果片段里没有答案，
> 就明确说"未找到相关规定"」

而闭卷基线**根本没有片段** —— `build_prompt` 在上下文为空时只给题目，
但**系统提示词没跟着换**。
于是模型看到"只能依据资料片段回答"却找不到片段 → **合乎提示词地拒答**。

🔴 这一组的数字会变成"闭卷基线 key_point 覆盖率 = 0"，
和检索组的差距被**凭空放大** ——
但那不是"检索有用"，是**基线被废了**。
PRD 7.4 早就警告过："B1 的口径必须写清楚，否则 B1 与 B3 的差距会被质疑"。

**解法**：**每个配置用自己该用的提示词**，并把用了哪套**落盘**：

| 配置 | 系统提示词 | user prompt |
|---|---|---|
| `retrieval`（主配置） | `SYSTEM`：只能依据【资料片段】、用 `[[Cn]]` 标注来源 | 带编号的模板 |
| `closed_book`（B1a） | `CLOSED_BOOK_SYSTEM`：**根据你已有的知识回答**、不知道就说不知道 | 只给题目 |
| `full_doc`（B1b） | `SYSTEM_NO_CITE`：依据给到的资料回答、**不提编号** | 全文模板，**去掉"按上面的编号引用来源"** |

🔴 `full_doc` 那处也踩了同一个坑：
全文基线给的资料**没有 `[C1]` 编号**，
user prompt 却要求"按上面的编号引用来源" —— 模型要么编编号、要么不答。

**修完的效果**（同 2 题，闭卷）：

> 「不知道。现有知识中没有"两份榆林制度"及其中"2023年制度"的具体文本，
> 无法可靠比较……请提供两份制度的名称、发布时间及相关条款原文或截图。」

这才是**诚实的闭卷基线**：语料是真实的地方政府文件，
通用模型**不可能背下来** —— 于是"检索是必要的"这句话才站得住。

**教训**：🔴 **基线的第一职责是"公平"，不是"好看"**。
一个被自己的提示词废掉的基线，
会让对照实验得出**比真相更强**的结论 ——
而结论越强，越不容易被人当场质疑，越容易在面试里被追问时崩掉。

🔴 附带一条工程经验：**改完代码但进程已经在跑，内存里的旧代码不会变**。
本轮就是在跑完检索组之后掐掉旧进程，
用新代码重跑两组基线 —— 所以"什么时候改代码"也是一项调度决策。

## K-42 · 🔴 `key_point_coverage` 只有 16.8% —— **87% 的未命中是度量产物，不是模型答错**

**现象**：生成层检索组跑完（306 题，489 秒），
`key_point_coverage` 分题型是：事实题 **0.168** / 数值题 0.443 /
版本陷阱题 0.133 / 跨文档推理题 0.127。

这个数低到不像模型能力 —— 但同一批答案里，
拒答误答率只有 2.4%、引用有效率 100%、版本召回 97.5%–100%。
**指标之间自相矛盾**，说明问题出在指标，不在模型。

**根因**：M2 的一条设计决定 —— key_point 必须**对齐成原文片段**
（`src/eval_align.py::align_key_point`，取与原文的最长公共连续子串），
目的是让"命中"可复核（答案里必须真的出现这段原文）。
但对齐产物有两个副作用：

1. **片段很短**（实测中位数 **10 字**、最短 2 字），
   于是常**从短语中间切断**：`"试生产前企业开"`、`"处理落实情况:202"`；
2. **带着原文的列表符号**：`"a.作业人员出现身体不适"`、`"(六)生产经"`、`"10.当"`。

而模型回答时说的是 `"作业人员出现身体不适"`（没有 "a."）、
`"T—4200 的正常操作压力范围为 35～50 kPa"`（语序与单位写法都不同）——
**答对了，字面包含判定却不成立**。

**实测失败分类**（真实运行产物，309 条未命中）：

| 类别 | 条数 | 占比 | 性质 |
|---|---|---|---|
| 改写 / 换词（语序、单位写法不同） | 193 | 62% | 度量产物 |
| 片段过短（< 6 字，多是数值残片如 `15m`） | 55 | 18% | 度量产物 |
| 仅列表符号差异 | 22 | 7% | 度量产物 |
| 模型整体拒答 | 39 | 13% | **模型真的错** |

→ **87% 的未命中不是模型能力问题**。

**解法**：**两个尺子都报，不合并、不换算**。

- **严格**：`kp ⊆ answer`（字面包含）—— 保守、可复核，原样保留；
- **软**：key_point 的**字符二元组覆盖率** ≥ 阈值（**顺序无关**，容忍语序与写法差异）。
  阈值取 **0.7**，并把 0.6 / 0.8 两档一起落盘做敏感性 ——
  阈值不能挑，选之前就把三档算出来。

实测（检索组，306 题）：事实题 **0.168 → 0.430**；
在"模型整体拒答"的题上软匹配只命中 8/45（**不会把拒答题算成命中**）。
另配一个**离线重算**模式（`--rescore <answers.jsonl>`），
改口径不必重跑 API。

🔴 **少于 4 个字的片段不做软匹配** —— `"15m"`、`"1m"` 这种数值残片
靠字符二元组匹配毫无意义；数值题另有 `must_include_numbers` 这个保真锚点。

**教训**：🔴 **指标的数值低，不代表模型差** ——
先问"这个指标在量什么"，再问"模型做得怎么样"。
本轮的分界线是：**同一个数字与其它指标互相矛盾**（召回 97.5%、引用 100%，
唯独覆盖率 16.8%），这种矛盾是指标坏了的信号。

🔴 附带一条更普适的：**指标口径变更不该逼着把 API 重跑一遍**。
逐题明细里存着原始回答和 key_point 清单，就能离线重算 ——
否则"改一次指标"= "再烧一遍额度"，
指标就永远不敢改，**错的指标会被一直用下去**。

## K-43 · 🔴 数值精确匹配率被**单位形态**系统性压低 —— `0.5t` 与 `0.5吨` 判成不同

**现象**：从失败样本里逐条看，发现这一条：

> 题：起重机械的额定起重量限值是多少？　key_point：`0.5t` / `1t` / `2m`
> 答：**额定起重量大于或等于 0.5 吨的升降机**；**大于或等于 1 吨**；提升高度**大于或等于 2 米**

🔴 **模型答得完全正确**，而 `numeric_exact_match_rate` 判它没命中 ——
因为语料里的数值带的是 **ASCII 单位**（`0.5t`、`500 mm`、`24 小时`），
模型回答时用的是**中文单位**（`0.5吨`、`500毫米`、`15分钟`）。
`normalize_number()` 只做了全角→半角、去空格、大小写统一，**没折单位**。

同类还有：`500 mm` vs `500毫米`、`1m` vs `1米`、`24 小时` vs `24小时`。

**根因**：`normalize_number` 的单位词表是空的 ——
"数值要归一化"这条（PRD 7.3）只落实了**数字形态**，没落实**单位形态**。
而这个语料是中文的、单位天然是中文的，
"语料写 ASCII 单位、模型写中文单位"是**必然**而不是偶然。

**解法**：

1. `normalize.fold_unit()`：把**数字之后紧跟**的 ASCII 单位折成中文单位
   （`t→吨`、`kg→千克`、`m→米`、`mm→毫米`、`cm→厘米`、`m3→立方米`、
   `min→分钟`、`h→小时`、`s→秒`）；
   🔴 **顺序要紧**：长单位必须先折（`m3`/`min`/`mm` 要在 `m` 之前），
   否则 `m3` 会先被折成"米3"。
   🔴 **只折数字之后的**：`T-4200` 里的 `t`、`5m` 里的 `m` 不会被误折。
2. 🔴 **答案侧也要折**（`normalize.match_num_norm`）——
   只折 key 侧的话，"答案写 `0.5t`、key 写 `0.5吨`"这种组合仍然对不上。

**实测影响**：数值题 `numeric_exact_match_rate` **0.443 → 0.506**（+6.3 个点）。
这 6.3 个点**不是模型挣来的，是口径挣来的** —— 报告里必须这么写。

**教训**：🔴 **归一化要覆盖"值的全部形态"，不是只覆盖数字本身**。
数字有三种形态要归一：**字形**（全角/半角）、**单位**（ASCII/中文）、**写法**（`15分钟左右`）。
本项目前两种漏了，第三种至今没解决（见 `notes/失败样本.md`）。

🔴 附带一条判据：**"正确答案被判错"是指标 bug 的第一信号** ——
看到一条明显正确的答案没命中，第一反应应该是"我的口径对不对"，
而不是"模型是不是不行"。这两者的修复动作完全相反。

## K-44 · 🔴 HTTP 错误体会**回显 API key**，而错误信息是要提交的产物

**现象**：换 key 之后第一次跑评测，306 题全部失败，
错误信息长这样（来自 `eval_runs/*.json` 的 `errors` 字段）：

```
RuntimeError: LLM 调用失败（重试 4 次）：HTTP 429: {"type":"error","error":
{"type":"rate_limit_error","message":"已达到 Token Plan 用量上限：...","request_id":"..."}}
```

一开始只当是"额度耗尽，换把 key 就行"。但**在写报告整理错误日志时才发现一个更严重的问题**：

🔴 **错误响应体经常回显请求里的 key**
（形如 `invalid api key: sk-xxxxxx`），而 `run_generation_eval.py` 会把
`errors[:20]` **原样写进 `eval_runs/*.json`** ——
`eval_runs/` 是**要提交进仓库的目录**。
→ **凭据会通过"错误日志"这条路径落进版本库。**

这不是假想：`llm_client.call_llm()` 拿到 HTTPError 时，
`e.read()` 出来的响应体**没有任何过滤**就拼进了 `last_err`。

**根因**：脱敏被放在了"落盘时"该做的位置，而**没放在"生成错误信息的那一刻"**。
正确做法是**在源头脱敏** —— 一旦拼进 `last_err` 的字符串，后面无论它流向
异常、日志还是 json，都已经是干净的了。

**解法**（`src/llm_client.py`）：

1. `_redact(text, key)`：先整体替换**本进程实际用的那把 key**，
   再用正则 `sk-[A-Za-z0-9_\-]{8,}` 兜底打码（防止别的形态漏网）；
2. 在 `HTTPError` 分支里、**拼 `last_err` 之前**调用；
   网络异常分支同样过一遍；
3. 新增 `tools/probe_llm.py`：**只打印端点与模型名，
   key 连前缀都不显示**（只报"已加载 N 字符"），
   探测结果落盘时也不含任何凭据字段。
   → 换 key / 换端点后**先探一下**（一条极短的问句），
   别直接开跑几百题 —— 失败原因（过期 / 模型名不对 / 端点不通）
   在评测脚本里长得一模一样。

**🔴 附带挖出一个更隐蔽的 bug：`.env` 的优先级写反了。**
`load_config()` 原本是：

```python
cfg.update(_parse_env_file(ROOT / ".env"))     # 本项目
cfg.update(_parse_env_file(FALLBACK_ENV))      # 兄弟项目  ← 后读的覆盖先读的！
for k in (...):                                # 环境变量
    if os.getenv(k): cfg[k] = os.getenv(k)
```

**后者覆盖前者** → 兄弟项目的 `expense-precheck/.env` **覆盖了本项目的 `.env`**。
后果：在本项目 `.env` 里换 key **完全不起作用**，现象是
"明明改了 key，端点还是说额度用完"—— 极容易误判成"key 没生效/端点不对"，
实际是优先级反了。已改成 `兄弟 < 本项目 < 环境变量`。

**教训**：
1. 🔴 **凭据不能只考虑"不打印"，要考虑"不落进产物"** ——
   错误日志是最容易被忽略的一条路径，因为它"看起来只是调试信息"。
2. 🔴 **"我改了配置但没生效"的第一嫌疑是优先级，不是配置内容** ——
   尤其当有多个配置来源（本项目 `.env`、兄弟项目 `.env`、环境变量）时。
3. 🔴 顺带说明一个权限模式的现实：auto mode 的分类器会拦
   "跑一个会读取真实凭据的脚本"。**被拦不是 bug** ——
   它提示的方向是对的：先让脚本本身做到"不打印凭据"（`probe_llm.py`），
   分类器就能放行；把脱敏做进脚本里比在说明里更有用。

## K-45 · 🔴 多路 RRF 的**坐标系撞车** —— 第二路被整路吞掉，症状像"方案没用"

**现象**：写多路检索（主索引 + 表格索引）时，融合结果里
**表格路的块一个都进不来**（"辅助路占 0 个名额"）。
第一反应是"表格索引没用" → 差点把这个方案直接判死。

**根因**：`bm25.rrf_fuse` 拿 **chunk_idx** 当 key。
而**各路的 chunk_idx 不在同一坐标系** —— 主索引第 3 块 ≠ 表格索引第 3 块。
两路的 idx=3 被当成同一个 chunk 融合，反查时又只认第一路 →
**第二路的块被整路吞掉**。

**解法**：融合**之前**给每路的块编**全局连续号**（第 ri 路局部下标 i → `offsets[ri] + i`），
融合后按号反查回 (路名, 局部下标)。

**教训**：🔴 **"多路方案无效"这个结论，必须先排除实现 bug 再下**。
症状（第二路没进结果）同时对应两种完全不同的原因：
"这一路没用"和"这一路被吞了"——**修复动作完全相反**（换方案 vs 改代码）。
判别办法：**先单跑那一路**，看它自己能不能召回。

## K-46 · 🔴 RRF 的权重是**门槛式**的 —— 没有中间态

**现象**：给辅助路加权 0.2 / 0.3 / 0.5 / 0.7，结果**辅助路一个都进不了 top-5**；
权重 1.0 时辅助路**占掉 40% 的名额**，把正文块挤出去，R@5 掉 6 个点。

**根因**：RRF 只用排名不用分数（PRD 4.3 的设计）。
辅助路第 1 名的分是 `w/(k+1)`，主路第 5 名是 `1/(k+5)`。
- `w = 0.7`：`0.7/61 = 0.0115` < `1/65 = 0.0154` → **永远挤不进去**
- `w = 1.0`：辅助路每个块都有 `1/61` 的分 → **每个都能进** → 挤掉正文

**教训**：🔴 **RRF 融合对"补充一路新内容"这件事天然不友好** ——
新路要么全进（挤占名额），要么全不进，**权重调不出中间态**。
所以"加一路索引"这个思路在 RRF 架构下**不是旋钮，是开关**。
想清楚这一点，能省掉一整轮参数扫描。

🔴 附带：同一张表**既在主索引（碎片）又在辅助索引（整块）** →
两份都拿高分 → top-5 被同一张表占满 → 正文被挤。
**多路不是"多一份信息"，是"多一份重复"。**

## K-47 · 🔴🔴 命中判定**没截断到 top-k** → 结论直接反转

**现象**：诊断脚本第一版算"双路 RRF"的 top-5 命中时，
**忘了把结果截断到 top-5**（实际取了 15 个块去判命中）。
于是：

| | R@5（第一版，未截断） | R@5（修正后，截断到 5） |
|---|---|---|
| 主索引单路 | 0.854 | 0.854 |
| **多路双路** | **0.899**（+4.5 点） | **0.793**（−6.1 点） |

🔴 **一个失败的方案，被这个 bug 变成了"提升 4.5 个点"的方案** ——
方向完全相反，结论完全相反。

**教训**：
1. 🔴 **"命中"的定义必须和"top-k"这个参数绑定** ——
   判 top-5 命中，就只能在**前 5 个**里判。
   用 15 个块去判 top-5 命中，等于把 top-15 的成绩记成 top-5 的账。
2. 🔴 **指标变好看时先怀疑指标**。第一反应应该是"我的口径对不对"，
   而不是"方案真的有效"。**涨得越漂亮，越要查。**

## K-48 · 指标标签会随参数**漂移** —— "R@5"其实是 R@top-k

**现象**：扫 top-k（5/8/12）时，打印出来的标签一直写"R@5"，
但取的是 `retrieve(top_k=args.top_k)` 的结果 → **标签是 R@top-k，不是 R@5**。
扫出来的三组数字**根本不能横向比**，却长得像同一指标。

**修法**：命中一律按**前 5 名**判（标签写什么就判什么），
覆盖度用 top-k 全量算（覆盖度本来就是"带进了多少"的量，天然随 top-k 变）。

**教训**：🔴 **指标名里写死的那部分，才是这个指标的契约**。
R@5 的契约是"只看前 5"；覆盖度没有这个契约，它天生随 top-k 变。
**扫参数前先把指标的契约和会变的部分分开写清楚**，否则扫出来的是三组不同的指标。

## K-51 · 🔴 主体靠正则从题干抽 → 中文主体匹配不到 → **误答被降级成"人工复核"**

**现象**：多机制拒答题（主体是"加氢反应器""液氩""催化剂再生"这类**中文**）
算出来的误答率**明显偏低**，而且偏低的方式很怪：
不是"漏判成通过"，而是"该算误答的被算成人工复核"。

**根因**：`scoring.refusal_judgement` 的主体来源是

```python
_TAG_RE = re.compile(r"\b[0-9A-Z]{1,8}(?:-[0-9A-Z]{1,8}){1,4}\b")
```

→ **只认位号形态**（`T-9001`）。中文主体**匹配不到** → `subject=None`
→ `if subject:` 那条分支（"主体被肯定句规定 → 误答"）**整条静默失效**。

**危害不是"漏判"，是"降级"**：

| 答案形态 | 传了 subject | 没传 subject |
|---|---|---|
| 「未找到 X 的规定。但 X 应每 30 **日**检修一次。」 | `false_answer` | `manual` |
| 「未找到 X 的规定。但 X 应每 30 **天**检修一次。」 | `false_answer` | **`pass`** ← 误答算成通过！ |
| 「未找到 X 的规定。但 X 检修按第三条执行。」 | `false_answer` | `manual` |

`manual` 会被排除在"可判样本"之外（PRD 7.3）→ **误答率被系统性低估**。

**解法**：主体从**数据集字段** `equipment_id` 传入，不靠正则猜：

```python
SC.refusal_judgement(ans, subject=q.get("equipment_id"), question=q.get("question"))
```

**教训**：
1. 🔴 **主体是数据集的字段，不是从自然语言里"解析"出来的**。
   凡是"从题干抽 key"的设计，都要问一句：**换一种主体形态会不会静默失效？**
2. 🔴 **静默失效比报错危险**：这条分支不抛异常、不打日志，只是**不执行**。
   判分变宽 → 数字变好看 → 没人会发现。
   → **必须有单测锁住"传 subject"和"不传 subject"的差异**
   （`tools/test_refusal_multitype.py` 里那条 `test_chinese_subject_degrades_without_subject`
   **故意断言缺陷存在**，防止将来有人把 `subject=` 参数删掉）。

## K-52 · 🔴 `--rescore` 只重算 key_point / 数值，**不重算拒答判定**

## K-53 · 🔴 拒答判定**只有一个口径** → "模型不会拒答"和"口径过严"混成一个数字

**现象**：150 条拒答题，严格口径误答率 **0.287**。
但逐条看失败样本，发现绝大多数答案**其实明确说了"未找到"**：

> 「加氢反应器的**具体检修隔离步骤和安全停机条件**，现有资料中未找到直接规定，
> **不能据此编造**。……检修前应结合**加氢反应器**内部可能存在的缺氧窒息、
> 中毒、燃爆等风险进行辨识，并落实相应安全措施。」

**根因**：PRD 7.1 的判定表把"**表态拒答**"和"**给主体下规定**"合成了一条判据，
于是"表态了但顺手把通用条款套到主体上"被算成**误答**。
这个答案在安全场景里其实是**负责任的**（它说了"不能据此编造"），
判成误答让人以为模型**不会拒答**。

**解法**：加**宽松口径**（`mode="lenient"`）—— 只问"有没有明确说资料里没有"，
不追究是否附带通用条款。两个口径都报：

| 口径 | 误答率 | 回答的问题 |
|---|---|---|
| 宽松 | **0.013**（2/150） | 模型有没有说"资料里没有"？→ **基本都会** |
| 严格 | **0.227**（34/150） | 有没有给不存在的装置下规定？→ **经常** |

更进一步：把两个口径**交叉**成三种行为模式，才看得清模型到底干了什么：

| 模式 | 严格 | 宽松 | v2 占比 |
|---|---|---|---|
| 1 完全没意识到 | 误答 | 误答 | 2.0% |
| **2 表态但归因污染** | 误答 | 通过 | **26.7%** |
| 3 完全正确 | 通过 | 通过 | 67.3% |

**教训**：
1. 🔴 **一个指标回答一个问题**。要问两个问题就得有两个指标；
   只报一个，读者无法知道数字反映的是哪一面。
2. 🔴 **两个指标要交叉看**。只看宽松，模式 2 和 3 混成"通过"；
   只看严格，模式 1 和 2 混成"误答"。**交叉后才有可执行的结论**。
3. 🔴 **口径选择会改变"改进方向"**：
   * 严格口径指向"**少给上下文**"（砍 top-k）；
   * 宽松口径指向"**生成层做归因隔离**"（要求标注通用要求的适用性）。
   选错口径，就会往错误方向优化。

## K-55 · 🔴 新增判定态会造成**分类假象迁移** —— "行为大幅改善"可能只是分类顺序变了

**现象**：给拒答判定新增了一个 `bounded` 判定态（"表态了 + 显式做了归因隔离"），

| 2 归因污染 | 40 (26.7%) | 21 (14.0%) ✅ |

**解法**：🔴 **判定分类的计数不能单独作为证据**，

| 明确说"该主体没有专门规定" | 68.7% | **96.7%** | ✅ 这才是真改善 |

**教训**：
1. 🔴 **新增判定态时，先想清楚它的优先级**，并检查
   "旧分类的样本是不是被新分类抢走了"。**分类计数一降，先怀疑分类顺序，再怀疑行为**。
2. 🔴 **报告行为模式分布时，必须同时给出至少一个与判分无关的行为指标**，

## K-56 · 🔴 改提示词必须**同步改判分**，且判分改动要验证**不影响历史批次**

**现象**：为了治"归因污染"，给系统提示词加了两层约束（句式 + 边界声明）。
但改完提示词直接跑，发现**看不出效果** —— 因为判分还是老的，
模型明明写了"其适用性不等同于对 T-9041 的专门规定"，判分还是判它"给主体下了规定"。

**根因**：判分规则和提示词是**成对**的。只改一边：
* 只改判分 → 指标变了，但模型行为没变 → **假的改进**；
* 只改提示词 → 行为变了，但指标没变 → **假的无效**。

**解法（两步，都不能省）**：

1. **同步改判分**：新增 `bounded` 判定态，判据是
   **同一个句子里**同时有主体和**强边界词**。
   * **弱边界词不够**（`通用要求` / `一般性规定` 单独出现不算）——
     模型可以在结尾随便加一句"以上是通用要求"，正文照样写「结论：<主体> 应……」；
   * **边界声明不能豁免真正的归因污染** —— 若另有「结论：<主体> 应…」一句，仍判误答。

2. 🔴 **验证新判分不影响历史批次**（否则两批不可配对比较）：
   用 `--rescore` 重算旧批次，核对数字**逐字不变**。
   本轮实测：主集 42 条判定**完全不变**（pass 39 / false_answer 1 / manual 2）；
   扩展集误答率不变（0.2867），仅多出 5 条 `bounded`
   （旧提示词下模型偶尔也会自己做归因隔离，5/150 = 3.3%）。

**教训**：
1. 🔴 **指标口径变了，要先证明它对旧数据是"惰性"的**（旧数据的判定不变）。
   否则"新批次比旧批次低"里，有多少是行为改进、有多少是口径漂移，**分不开**。
2. 🔴 这与 PRD 5.4 的原则不冲突，但要划清边界：
   **结构化事实**（版本状态）→ 代码强制拼接；
   **推理过程**（通用条款的归属）→ 代码代劳不了 → 提示词 + 判分双管齐下。
   但**服从率永远不是 100%**（本轮实测 96.7%）→ 判分侧的兜底是**必需品**。

## K-57 · 🔴 判据的「全局豁免」过宽 → 放过了**结论式断言**

**现象**：为了修「边界声明只按单句判 → 假阳性」，
把豁免改成"答案整体有边界声明时，后续含主体的断言句一律不算污染"。

**根因**：豁免条件只查了「**有没有具体数值/条款号**」，
漏了「**这句话是不是把义务绑定到了通用来源上**」：

```
「因此，T-9042 检维修至少应按通用流程办理作业许可」  ← 复述通用要求（豁免）
「结论：设备 T-9041 的检维修应履行作业许可手续」    ← 给主体下结论（不该豁免）
```

第二句既无数值也无条款号 → 被第一版的豁免条件放过了。

**解法**：豁免要**两个条件同时成立**：
A. 没有具体数值/条款号；B. 句中有**通用来源限定语**
（`按通用流程` / `依上述一般要求`）。

**教训**：🔴 **判据的豁免条件要逐条问"它会不会放过另一种错误"** ——
"无数值/条款号"这条豁免，拦得住"编造具体参数"，拦不住"泛泛地下结论"。

## K-58 · 🔴🔴 正则的**子串陷阱** + 字符类**漏中文引号** → 18/24 条是假阳性

**现象**：拒答误答率怎么修都降不下来（`system_v2` 卡在 0.153）。
逐条打印被判污染的句子，发现**一大半根本不是污染**：

```
「结论：资料中没有“聚丙烯装置”的专门规定」        ← 模型在承认没规定，被判成污染
「但该原文针对游乐设施，不属于乙烯裂解装置的专门要求」 ← 模型在澄清归属，被判成污染
「这些内容需要由乙烯裂解装置适用的专项应急预案…确定」 ← "应急"里的"应"，被判成断言谓语
```

**根因（三处，都很典型）**：

1. 🔴 **字符类没覆盖模型真实输出** ——
   `_NEG_PATTERN` 写的是 `没有\s*[一-龥A-Za-z0-9]`，
   而模型写的是「没有**“**聚丙烯装置**”**」→ 紧跟的是全角引号 `“`
   → **否定句被判成肯定句**。（与 K-39 同款：字符类是按想象写的，不是按实测写的）
2. 🔴 **子串陷阱** ——
   `_ASSERT_RE` 里的 `应` 会命中「**应急**预案」「**应用**」「**相应**」；
   `设置` 会命中「盲板**设置**」（名词短语）；`属于` 会命中「**属于何种**设备」。
3. 🔴 **否定词族覆盖不全** ——
   `不(?:适用|存在|明确|…)` 里没有 `属于`/`是`/`针对`
   → 「不属于 X 的专门要求」判不出否定。
4. 🔴 **「待补充/待确定」表述没被认出来**（**端到端批次才暴露**）——
   「需结合其工艺特点…**另行确定**」「实际**应结合**设计文件…**编制**专项维保规程」
   是模型在说"这些要结合实际情况定"，是**负责任的不确定**，不是给主体下规定。
   → 端到端批次 7 条"污染"里 **4 条**是这一类；修掉后 7 → 3。

**解法**：字符类补中文引号/书名号/括号；`_ASSERT_RE` 加前后视
（`(?<![相适供反])应(?![急用])`、`属于(?!何|哪|什么)`、`是(?!否)`）、
去掉「设置」；否定词表补「不属于/不是/不针对/缺少」；
`_CONDITIONAL_RE` 补「另行确定/另行编制/进一步确定」与
「(应|需|须)(结合|根据|依据)…(判断|确定|评估|编制)」。

⚠️ **「为」「是」必须保留** ——「检修周期**为** 30 天」「作业许可**是** X 规定」
这类真规定句靠的就是它们，去掉会造成假阴性。

**教训**：🔴 **正则的字符类和词表是"想象"出来的，不是"实测"出来的**。
写完判据一定要**逐条打印被判中的句子人读一遍**，
否则数字会一直卡在一个"看起来合理但其实是噪声"的位置。

## K-59 · 🔴 判据收紧让数字变好看 → 必须**主动查漏判**

**现象**：修完假阳性，`system_v2` 误答率从 0.160 → **0.040**。
数字好看得可疑 —— 是修对了，还是把真污染也放过了？

扫**所有**"含主体 + 含断言谓语 + 含具体数值/条款号"却被排除的句子：

  （1123 批次与端到端 1457 批次**都是 0 条**）；
* **中风险（只有断言谓语）**：443 条 → 抽样 14 条**全部是正确排除**

**教训**：🔴 **"指标变好"本身是可疑信号**，不是好消息。

配套工具：`tools/diag_pollution_fp.py`（逐条打命中原因）、
`tools/scan_pollution_missed.py`（反向扫漏判）。

## K-60 · 🔴 代码兜底只「追加一句声明」治不了归因污染 → 必须**动正文**

**现象**：代码级兜底第一版 = 在答案末尾追加一句
「以上引用均为通用规定，不构成对 X 的专门规定」。
实测（150 条旧 system）：**只把误答率从 0.287 压到 0.273（降 2 条）**。

**根因**：模型正文里那句「结论：<主体> 应……」**原样还在**，
末尾补一句"这些是通用的"是**自相矛盾**的 —— 用户读到的仍然是
"它说 T-9041 应该怎样，然后又说不算"。

**解法（两级，缺一不可）**：
1. **就地划除**：把污染句用删除线标出（`~~结论：……~~`）+ 末尾汇总
   「🔴 不予采信：答案中有 N 句把通用条款表述为 X 的专门规定」；
2. **末尾声明**：召回块里根本没出现这个主体时补归因声明。

**实测效果**（150 条，配对对比）：

| | 模型层误答率 | 最终输出误答率 | 输出层残留污染 |
|---|---|---|---|
| 旧 system（无提示词约束） | 0.207 | **0.000** | **0 句** |
| `system_v2`（有提示词约束） | 0.040 | **0.000** | **0 句** |

**教训**：🔴 **提示词治「模型说什么」，代码治「用户看到什么」，两者正交**：
`system_v2` 下模型层已降到 0.040，但兜底仍划除了 **7 句**残留污染
→ 说明代码兜底**不是**提示词的重复。
但也**绝不能**把"最终输出 0 误答"说成"模型学会了" ——
代码保证的是输出安全，不是模型行为（K-55 的教训在这里同样成立）。

## K-61 · 🔴 跨判据版本的数字**不能直接比** → 要把每版判据都跑一遍同一批答案

两个数字**分别来自两版判据**（v0 和 v1）—— 形式上是跨口径比较。

## K-62 · 🔴 **证据标记泄漏进 key_point** —— `【yulin_do` 这种碎片

**现象**：跨文档推理题的 key_point 长这样：

```
「【yulin_do」        「【yuli」        「第七条动火和受」
```

在原文里**根本不存在** → `key_point_coverage` 的分母是垃圾。

1. `doc_evidence()` 给 LLM 的证据文本每份文档前面加一行 `【<doc_id>】`

**教训**：🔴 **给 LLM 的证据加任何标记，都要想到"模型会学它"**。

## K-63 · 🔴 **"自证自洽"是最危险的假阳性来源**

**现象**：质检报告说"事实题 key_point 不可达：4 条"，但人工看下来大部分是可达的。

**根因**：质检在 **`gold_answer` 里**查 key_point 是否可达，
而 `gold_answer` 与 `key_points` **来自同一次机械切片** → 两边一起错 → 检查永远通过。

**更深一层**：事实题的 key_point 本身就是**按 `clause_no` 切片的产物**
（"七,事故调查7.1事故调查市市场监督管"—— 停在"管"字，还跨了两个条款）。
与 K-08（题干截断）**同款根因**：切点落在词中间。

**修法**：
1. **溯源核对必须回到原文，且要到条款级**（用 `data/chunks/clause.jsonl` 的条款原文）；
2. **key_point 改用 LLM 从检索到的证据里重新提炼**，逐字片段 + 机器校验字面可达
   （`tools/refine_key_points_llm.py`，检索用的是项目自己的 BM25）。

**教训**：🔴 **当"检查"和"被检查的数据"来自同一次加工时，检查通过不代表数据对。**
这是评测工程里最隐蔽的一类假阳性 —— 必须问一句"**这个检查在独立的数据上做过吗**"。

## K-64 · 溯源条款错位 → **gold 区间错了，召回数字就不可信**

**现象**：预案型 / 表格型文档里，题目的 `clause_no` 指向一个**只有标题的 chunk**
（14 个字），而答案内容在**下一个兄弟章节**里。

**为什么严重**：`clause_no` 决定评测的 **gold 区间**（R@5 的命中判定、

**修法**：`tools/fix_review_findings.py` 把 `clause_no` 改到锚点**实际所在**的条款

⚠️ **数值题不改** —— 数值题的"题干问的量 ↔ 锚点"是否对应，机器判不了

**教训**：🔴 **溯源元数据不是"注释"，它参与计算**（gold 区间）。

## K-66 · 🔴 **诊断脚本自己"全绿"的时候，先怀疑键对不上**

**现象**：新写的 `tools/diag_boilerplate_impact.py` 跑出来
"块内噪声字符占比均值 **0.00%**、噪声 ≥50% 的块 **0**"——
数字太干净，反而像假阴性。

**根因**：噪声表用**文件名**（`xxx.md`）做键，

🔴 **这与 K-13 同源**："数据有问题"和"判据用错字段"在报告里长得一模一样，

```python
chunk_docs = {c.get("doc_id") for c in chunks}
hit_docs = chunk_docs & set(boiler_frags.keys())
if not hit_docs:
    raise SystemExit("🔴 键对不上：噪声表与 chunk 的 doc_id 无交集，结果不可信，终止")
```

**教训**：🔴 **任何"占比 0%"的结果都必须先自检键能不能对上**，
否则报出去的是"没问题"，实际是"没查"。这与 K-58「子串陷阱」、

|---|---|---|
| 形态 | 「试生产前企业开」← **停在词中间** | 「试生产前企业开展了设备及管道试压、吹扫、气密…」← 完整句 |
| 逐字包含 | **容易**（碎片短，答案里抄到这 5 个字就算命中） | **难**（要逐字复现整句） |
| bigram 覆盖率 | 低（碎片本身信息少） | **高**（整句覆盖了答案的多个片段） |

🔴 **所以旧 kp 的"严格命中"不是因为模型答得准，是因为碎片好凑** ——
上一轮判定「事实题严格口径 0.168 的分母里混着垃圾」是对的，
但**垃圾是往高了灌**，修完之后数字**更低**。

**做法**：🔴 **key_point 不进提示词**（只用于评分）→ 所以可以用
**同一批答案换一套 kp 重判**，得到零 API 成本的配对对比。
`tools/rescore_provenance.py --kp-source batch|testset` 就是这个用途，
且 `--kp-source batch` 已验证能**逐字复现** `tools/compare_generation.py` 的数字
（事实题 0.4297/0.168/0.2327 vs 权威 0.430/0.168/0.233）。

**教训**：🔴 **换判分口径后，数字可能变好也可能变差，事先不能假设**。
上一轮说"0.168 待重算"，本轮重算结果是 **0.064**（更差）→ **不能为了好看继续用旧口径**。

## K-69 · 🔴 **两个独立批次的误答率差，不能当结论 —— 必须配对**

**现象**：`system_v2` 6/150（0.040）vs `system_v3` 3/150（0.020），
看着是"减半"，但两个 CI（[0.019, 0.085] vs [0.007, 0.057]）**大幅重叠**。

**配对后（同一批 qid、同一检索结果、同一判据）**：
| | 数量 |
|---|---|
| v2 误答 → v3 通过 | **6** |
| v2 通过 → v3 误答 | **3** |
| 都误 / 都对 | 0 / 141 |
| **McNemar 精确检验** | **p = 0.5078** |

→ 🔴 **不显著**。要达到 p<0.05，需要 9 对里至少 8 对同向翻转。
→ **"0.040 → 0.020"目前只能说"方向一致，证据不足"**。

🔴 **反过来，宽松口径是干净信号**：v2 4/150 → v3 **0/150**。

**工具**：`tools/compare_refusal_paired.py`（两批次配对 + McNemar 精确检验 + 逐条翻转清单）。

**教训**：🔴 **K-65 的"配对设计"要在**跑批次之前**就定好**，
事后拿两个独立批次比，等于把"个体层面的翻转"的信息扔掉了，
只剩下两个**都带噪声**的总体数字。

## K-70 · 🔴 **"看起来像重大发现"的结论，被自己的第二个工具推翻了**

**原结论（错的）**：SYSTEM_V3 全量 150 条里，3 条误答中有 1 条是"前两轮没见过的新形态"：
「资料中有合成氨装置**检维修作业许可**的明确规定」
→ 判成"**假称语料里有规定**"（对语料内容本身的错误断言），
初版诊断测出 **8/150** 且"全部同时有'未找到'表态 → **自相矛盾**"。

🔴 **两处都错**：
1. **8/150 是假阳性** —— 宽松的模式把**边界声明句**
   （「以下为通用要求，其适用性不等同于对 X 的专门规定」）也判成了假称，
   而那恰恰是**我们想要的正确行为**。
   还踩了 K-58 同款的**子串陷阱**：「**现有**资料仅能说明…」里的"有"。
2. **"自相矛盾"不成立** —— 那句说的是**检维修作业许可**，
   答案后面说"资料中没有…**动火和受限空间管理**的专门规定"，
   **两个不同的子项**。

**修正后的实测**（判据复用 `src/scoring.py::find_corpus_claim_sentences`）：
假称 **1/150**，且这 1 条**同时也是污染句** → **不是独立的失败模式**，
就是原有的"归因污染"。

**修法**：
* 诊断工具**不再自带正则**，改为直接调用 `scoring` 里的判据
  → 判据只有一份，改一处两边同时生效；
* 判据里加两条排除：**边界声明句**（`_BOUNDARY_STRONG`）永远不是假称；
  "有"要用**否定回查**排掉「现/所/具/自/另/未/没/如/若」+「有」。

**教训**：🔴 **判据一旦有两份实现，就一定会有一份是假的**。
本条和 K-59 是同一个硬币的两面：K-59 是"判据收紧让数字好看"，
本条是"**判据宽松让数字好看**" —— 两者都要靠**第二个独立工具**去撞。
→ **凡是"新发现"，先问：这条结论有第二个实现吗？没有就别写进报告。**

⚠️ 代码级兜底的扩展**仍然保留**（安全网：假称句不一定同时满足污染句的全部条件），
但本批次**新增划除 0 条**，不改变任何已发布数字。

## K-71 · 🔴 **批次时间戳只到分钟 → 同分钟跑两个批次会互相覆盖**

**现象**：连续跑 L4 和 L2 两个检索批次（各约 10 秒），
两者时间戳都是 `20261106_1047` → **L2 把 L4 的产物整个覆盖了**。
L4 的数字只剩在日志里（`eval_runs/_l4_run.log`），JSON 已不可信。

🔴 这是 K-15「中间结果只写在输出文件里」的**另一个变种**：
K-15 是"下一步从原始重算会覆盖前一步"，本条是"**两次独立实验**撞了同一个文件名"。

③ 🔴 **对照时必须核对 `embed_backend` 字段** ——
`tools/compare_embed_backends.py` 现在会打印双方的 `embed_backend`，
如果两个批次后端一样就说明撞了。

**教训**：🔴 **批次的"身份"应该由内容决定，而不是由文件名决定**。
→ 对照脚本必须**先校验后端标签一致**，不一致就拒绝出表。

## K-72 · 🔴 装 `sentence-transformers` 的三个连环坑

**坑 1 · pip resolver 回退（最贵的一个）**
不钉版本时 `pip install sentence-transformers` 会一路回退到要 `pytorch-transformers`
的远古版本，然后卡在 `regex` 上：
`ERROR: Could not find a version that satisfies the requirement regex (from versions: none)`
→ 在 **13–27 kB/s** 的链路下，这个回退跑了 **50 分钟**还失败。

**修法**：`pip install --no-deps` + **钉死版本**
（`sentence-transformers==3.4.1` / `transformers==4.48.3` / `huggingface-hub==0.28.1`
/ `tokenizers==0.21.0` / `safetensors==0.5.2`），其余依赖本机已有。

**坑 2 · `HF_ENDPOINT` 设得太晚**
`huggingface_hub.constants.ENDPOINT` 是在**导入时**从环境变量算出来的。
原写法（`import sentence_transformers` **之后**才 `os.environ.setdefault("HF_ENDPOINT", ...)`）
→ endpoint 早就固化成了 `huggingface.co` → 本机 8 秒超时 → 模型下不下来。
→ **所有"影响库行为的环境变量"都必须在 import 之前设**。

**坑 3 · Xet 协议不可达**
`model.safetensors` 的下载会被**重定向到 `cas-bridge.xethub.hf.co`** → 本机
`Read timed out` → 必须 `HF_HUB_DISABLE_XET=1` 强制走传统 HTTP 路径。

🔴 三条都已固化进 `src/embed.py::try_l1()`（`setdefault` 全部提到 import 之前）。
⚠️ 另：`hf-mirror.com` 会**拒绝 `Python-urllib` 的默认 UA**（403）；
`huggingface_hub` 自带正常 UA 所以不受影响，但**手写下载脚本必须自己加 UA**。

## K-73 · 🔴 **判据的每一级都要问「它在长文本上还成立吗」**

**现象**：把 key_point 的可达性判据源从 `gold_answer`（短切片）换成
**来源文档正文**（整篇）后，不可达数从 46 骤降到 **3** —— 干净得可疑。

**根因**：`check_key_point_reachable` 的第三级判据是
「**字符集覆盖率 ≥ 0.8**」——
在短切片上这是真约束（高频字少），
在**整篇文档正文**上**几乎必然成立**（高频字把覆盖率拉满）
→ 实测把 **63 条真·跨文档 key_point** 判成可达（假阴性）。
那些 key_point 多是应急预案之间的通用套话
（"特种设备事故应急救援工作坚持'以人为本'的理念…"在多份预案里一字不差），
本该被抓住。

**修法**：判据**按源类型分级**（长源 `doc_md` 禁用「字符集覆盖」级，
只走「归一化后完全包含」→「前缀包含 85%」两级）：

```python
# tools/check_test_set.py
REACHABILITY_JUDGE = "v2"
allow_cc = (mode != "doc_md")     # 长源禁用字符集覆盖级
```

修正后不可达 27 条 —— 与另一个工具的 C1 箱**独立吻合**。

**教训**：🔴 **判据的分级不是"从宽到严"，而是"每级都有自己的适用域"**。
换判据源之后必须**单独跑一次松紧诊断**（同一批数据跑 4 种判据比对），
而不是直接看新数字。

## K-75 · 🔴 **数字骤降/骤升都可能是判据失效的信号**

**现象**：换判据源后不可达数 46 → 3。

**本能反应**：数字大幅改善 = 修对了。
**实际**：判据在长文本上失效了（K-73）。

## K-76 · 🔴 **"每题都要 key_point" 的适用范围比想得宽**

**现象**：质检规则只对**事实题**检查"缺 `key_points`"，
于是**跨文档推理题** `t_5310767fe3d2` 没有 key_point 也没被标记。

**危害**：该题在 `key_point_coverage` 里**分母为 0** → 被**静默跳过**
→ 跨文档推理题的实际分母是 24 而不是 25（统计口径与题集条数对不上）。

**修法**：
```python
# 非拒答题缺 key_points → key_point_coverage 无分母 → 该题会被静默跳过
if not kps and r.get("question_type") != "拒答题":
    flags["no_key_points"] = True
```

**教训**：🔴 **拒答题是唯一的例外**（它的 key_point 是判分标准，不是覆盖率口径）。
→ 凡是有"分母"的指标，都要问一句：**"哪些题会被分母为 0 静默跳过？"**
